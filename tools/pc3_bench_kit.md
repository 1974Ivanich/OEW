# pc3_bench_kit — стендовый комплект ПК-3 (v2)

Один пакет для оператора ПК-3: одна точка входа (`START_HERE_PC3.md`), свои инструменты,
свой образ прошивки, свой манифест. Комплект **не собирается руками** — состав берётся из
репозитория, чтобы документы и скрипты в комплекте не расходились с тем, что реально
проверено.

* документы комплекта — `docs/pc3_bench_kit/` (копируются в корень комплекта как есть);
* инструменты — `tools/pc3_bench/` (маппинг путей — `KIT_TOOLS` в сборщике);
* образ — внешняя папка сборки, SHA256 закреплён в `IMAGE_SHA256` сборщика.

## Сборка и проверка

```bash
# собрать комплект на носитель и тут же проверить (образ берётся из уже проверенного v1)
py -3 scripts/assemble_pc3_bench_kit.py --out <носитель>\pc3_bench_kit_20260926_v2 \
      --image-dir <носитель>\pc3_bench_kit_20260926\IMAGE

# проверить комплект, не меняя его (манифест + документы + прогон инструментов)
py -3 scripts/assemble_pc3_bench_kit.py --verify <носитель>\pc3_bench_kit_20260926_v2

# состав комплекта без сборки
py -3 scripts/assemble_pc3_bench_kit.py --list

# карантин: убрать устаревшие объекты с носителя и посчитать их хеши
py -3 scripts/assemble_pc3_bench_kit.py --quarantine-into <карантин> <объект1> <объект2>

# самопроверка без образа и без носителя (то же гоняет CI)
py -3 scripts/assemble_pc3_bench_kit.py --selftest
```

## Что проверяется автоматически

| Проверка | Зачем |
|---|---|
| манифест (`SHA256SUMS`): недостающие / изменённые / **лишние** файлы | состав комплекта равен заявленному |
| образ: SHA256 `firmware.bin`/`firmware.elf` == `IMAGE_SHA256` | нельзя подсунуть оператору другой образ |
| инструкционные документы: никаких абсолютных путей с буквой диска | «`E:` на чужой машине» — источник ошибок (дефект v1) |
| инструкционные документы: `vf_raw.py` только как `TOOLS\vf_raw.py` | инструмент должен быть там, где его ищет оператор |
| `START_HERE_PC3.md` и `TOOLS/HOWTO.md`: указание про кодировку консоли | иначе оператор по умолчанию работает в cp1251 |
| `--selftest` каждого инструмента **на копии из комплекта** при `PYTHONIOENCODING=ascii` | регресс `UnicodeEncodeError` (дефект v1) |
| `breakdiag_parse.py` на реальной усечённой строке из возврата ПК-3 | регресс `ValueError` (дефект v1) |
| компиляция всех `.py` комплекта | в комплект не попадает синтаксически битый файл |

Коды возврата сборщика: `0` — OK, `1` — расхождение/провал проверки, `2` — ошибка вызова.

## Инварианты комплекта

1. В комплекте ровно один исполняемый документ — `START_HERE_PC3.md`; остальное — протоколы,
   контекст и карантин.
2. Все пути в инструкциях — относительные от корня комплекта.
3. Любой документ/инструмент комплекта существует в репозитории (нет «только на носителе»).
4. Карантин `_SUPERSEDED/` лежит внутри комплекта, имеет свой `SHA256SUMS` и не является
   инструкцией.

## Отличия v2 от v1 (`pc3_bench_kit_20260926`)

* `enc_sign.py`, `breakdiag_parse.py`, `vflog_step_report.py`: вывод только символами cp1251 +
  `errors='replace'`; самотесты проверяют это явно (в v1 — падение на консоли Windows);
* `breakdiag_parse.py`: терпимый разбор (коды возврата 0/1/2/3), нет падения на усечённой строке;
* в комплект добавлен `TOOLS/vf_raw.py` (в v1 отсутствовал, хотя нужен на шагах 0–3);
* инструкции переведены на относительные пути, манифест описан в корне (в v1 был указан `IMAGE/`);
* создан фактический карантин `_SUPERSEDED/` (в v1 заявлен, но не существовал);
* `CONTEXT/SUPERSEDED.txt` переписан по фактическому состоянию носителя.

Образ прошивки не менялся: `firmware.bin` = `96e9747028a5bf6ff7bf87a4e825dbe930e43d4545b8dcaaa2f9a80538d11d64`.
