# ТЗ: interlock параметров двигателя в FOC_Start() (HEAD 01152a2)

**Проект:** OEW Motor Drive — STM32G474RE, CMSIS-only, OEW dual-inverter FOC, асинхронный двигатель.
**Характер:** interlock старта по значению Rs/Ls. НЕ изменение fail-closed политики карты,
НЕ автотюн, НЕ slip-модель. Default-deny карты реконструкции не ослабляется.
**Затрагиваемые файлы:** `src/foc.c`, `src/foc.h`, `src/cli.c`,
`tests/foc_start_gate_test.c`, `tests/cli_test.c`. Остальное — не трогать.
**Статус:** реализовано и проверено (см. §6). ТЗ фиксирует дефект, отклонённый
вариант и границы решения.

---

## 1. Дефект

`FOC_Start()` (`src/foc.c:520`, номера строк здесь и далее — после применения
патча) проверяет `VFC_IsRunning`, `g_clock_fail`,
`PROTECT_IsFault`, `CurrentRecon_IsReady`, initial PWM sample context, offsets —
и **ничего** про Rs/Ls. Значит доступен путь: прогнать `ch/chu/chv/chw`
(карта реконструкции), не запускать автотюн, дать `1` — FOC стартует на дефолтах.

Дефолт индуктивности:

```c
#define FOC_DEFAULT_L_UH 100   /* src/foc.c:176 — «уточнить автотюном!» */
```

Собственное окно валидности проекта (`src/autotune_math.h:11-14`):

```c
#define AT_MATH_SANE_LS_MIN_UH 500
#define AT_MATH_SANE_LS_MAX_UH 500000
#define AT_MATH_SANE_RS_MIN_MOHM 10
#define AT_MATH_SANE_RS_MAX_MOHM 100000
```

**100 мкГн в 5 раз ниже собственного минимума проекта.** Формулировка дефекта:
в FOC допускается значение индуктивности, которое `AT_SaneLs()` отверг бы как
мусор. Это значение уходит в `FOC_ComputePIGains()` (Kp/Ki по модульному
оптимуму), в `BEMF_Init()` (observer) и в `foc_lsigma_uH` — то есть в силовой
контур на реальном железе.

По Rs дефект отсутствует: `FOC_DEFAULT_R_MOHM 13000` (`src/foc.c:175`, 13 Ом)
лежит внутри 10…100000 мОм и действительно измерен.

## 2. Отклонённый вариант: гейт по `FOC_IsParamsApplied()`

**Отклонён. В третьем раунде не возвращать.** Причина — обходится, флаг означает
«кто-то что-то записал», а не «параметры измерены». Он поднимается в двух местах:

```c
int FOC_SetMotorParams(...) { ... params_applied = 1; }   /* src/foc.c:446, флаг на 476 */
int FOC_SetPIGains(int32_t kp, int32_t ki) {              /* src/foc.c:480-489 */
    ...
    params_applied = 1;                                   /* src/foc.c:487, motor_L_uH не тронут */
}
```

Два реальных пути обхода:

1. `piapply` (`src/cli.c:290-291`) → `FOC_SetPIGains()` — ставит флаг, **вообще
   не касаясь** `motor_L_uH`. FOC стартует с Lσ = 100 мкГн при `AP=1`.
2. `mp=Rs,Ls,...` (`src/cli.c:266`) → `FOC_SetMotorParams()`, где вся
   проверка — `if(r_mohm < 1 || l_uh < 1) return -2;` (`src/foc.c:448`). Вписанные
   руками 100 мкГн «применены», флаг = 1.

Дополнительно: `params_applied` — диагностика для GUI (`@AP:%d`, `src/cli.c:232`).
Делать из него interlock — смешать диагностику и interlock, что запрещено
`AGENTS_WORKFLOW`. Если когда-нибудь понадобится именно «измерено vs вписано
руками» — это **отдельный** флаг, который ставит только путь публикации автотюна
(`Autotune_*` → `AT_VALID_*` mask), а не `FOC_Set*`. Сейчас не нужен: проверка
значения закрывает риск.

### Поправка к числам предыдущего раунда

Разбор, на основе которого предлагался флаг-гейт, содержал ошибки по памяти —
фиксирую, чтобы они не осели в документации:

| Утверждалось | Факт |
|---|---|
| `SANE_LS` = 50…50000 мкГн | 500…500000 (`autotune_math.h:11-12`) |
| `SANE_RS` = 10…1000 мОм | 10…100000 мОм (`autotune_math.h:13-14`) |
| дефолт Rs = 1300 мОм | 13000 мОм = 13 Ом (`foc.c:175`) |
| «обходится через `p=`» | `p=%u,%u,%u,%u` (`cli.c:124`) — PWM-debug, не PI. Обход: `piapply` и `mp=` |
| таблица rc в CLI: 0…-4 | так и есть (`cli.c:136`), но она уже устарела — `-5` в ней отсутствовал |
| `FOC_SLIP_POLICY_MIN_TR_US` = 100 | 1000 (`src/foc_slip_policy.h:8`) — вывод про zero-slip при Tr = 60 мкс не меняется |

## 3. Требуемое решение: гейт по значению

Проверка **значения** Rs/Ls против существующего валидатора, а не флага. Свойства:

- не обходится через `piapply`/`mp=` — проверяется само значение;
- переиспользует окно `AT_MATH_SANE_*` — нового источника истины не появляется;
- ложных отказов по Rs нет: дефолт 13000 мОм проходит.

**Место гейта:** после проверок карты и initial context, до `FOC_Init()`.
Оба ограничения обязательны:

- **после** карты/контекста — иначе гейт подменит их причину отказа
  (`rc=-2 map_unverified` превратится в `-6` на стенде, где карта и есть проблема);
- **до** `if(!foc_initialized) FOC_Init();` — иначе отказ произойдёт уже после
  инициализации observer'а.

**Отдельный код возврата.** Переиспользование `-2`/`-3` недопустимо: оператор
читает причину из `@FOC:START:FAIL:rc=`, и неверная метка дороже отсутствия метки.

**Rs включён симметрично** с Ls: дефолт проходит, а вписанные руками через `mp=`
5 мОм — нет. Расширение против минимального варианта осознанное.

## 4. Инвариант дефолта — защита времени компиляции

Само по себе «100 < 500» — совпадение конфигурации, а не свойство системы.
Поднятие `FOC_DEFAULT_L_UH` до 500+ молча снимет гейт, и тесты останутся
зелёными. Поэтому инвариант «дефолт обязан лежать вне окна валидности»
закреплён на этапе сборки (`src/foc.c:177-181`):

```c
typedef char foc_default_l_uh_must_stay_out_of_sane_range[
    (FOC_DEFAULT_L_UH < AT_MATH_SANE_LS_MIN_UH) ? 1 : -1];
```

Проверено подменой дефолта на 600 мкГн:
`error: size of array 'foc_default_l_uh_must_stay_out_of_sane_range' is negative`.
`_Static_assert` не используется — сборка на `-std=c99`.

## 6. Тесты

`tests/foc_start_gate_test.c`, блок «Gate 3» — карта загружена, SD-линии здоровы,
`PWM_HardwareInterlockHealthy()` == true, то есть кейс изолирует именно параметры:

- воспроизводит оба пути обхода: `FOC_SetMotorParams(13000, 100, 150000)` → 0
  (мусорная Ls принята сеттером) и `FOC_SetPIGains(100, 10)` → 0;
- `assert(FOC_IsParamsApplied() == 1)` — **это и есть доказательство**, что
  флаг-версия фикса дыру не закрыла бы;
- `assert(gate_rc == FOC_START_PARAMS_OUT_OF_RANGE)` — точный код, не «любой отказ»;
- `test_adc_start_count == 0`, `test_adc_stop_count == 0`,
  `test_adc_calibrate_count == 0`, `assert_power_path_off()` — гейт срабатывает
  до `FOC_Init()`/ADC, силовой путь не тронут;
- ассерты неконфликтности `-6` со всеми шестью существующими кодами;
- позитивный контроль: Ls = 4920 мкГн → `FOC_START_OK`, иначе гейт неотличим от
  «блокирует всё»;
- Gate 1 (`rc=-2` при дефолтных параметрах) сохранён специально — он закрепляет
  требуемый **порядок** гейтов из §3.

Порядок работы был: сначала тест (падал на текущем коде именно на целевом
ассерте), затем патч. `make test-hosted` — полный набор зелёный,
включая `foc_start_gate_test: PASS` и `cli_test` (111+1 golden-проверок).

## 7. Остаточные риски и следствия

**Операционное следствие (главное).** С дефолтами FOC больше не стартует: до `1`
обязателен автотюн + `mpapply` либо явный `mp=` с измеренными значениями.
Это и есть смысл фикса, но стендовые чеклисты в `docs/`
(`BENCH_NEXT_STEP_PLAN_20260824.md`, `ACCEPT_CT_FIX_CHECKLIST.md`,
`docs/TZ_WEB_AI_CURRENT_MAP.md`) описывают старую последовательность и требуют
правки — иначе на стенде `rc=-6` прочтут как регресс.

**Сборка прошивки не проверена.** `foc.c`/`cli.c` проверены только host-компилятором
(`-Wall -Wextra -Werror`); ARM-тулчейна в окружении не было. Прогнать `make` перед коммитом.

**Сеттеры остаются разрешающими.** `FOC_SetMotorParams` по-прежнему принимает
любую Ls ≥ 1: interlock стоит на старте, а не на записи. Отбивать мусор на входе
`mp=` — отдельная задача, она меняет коды ошибок `mp=` и контракт GUI.

**Вне объёма этого ТЗ (зафиксировано, не исправлялось):**

1. **Молчаливый zero-slip.** `Tr < FOC_SLIP_POLICY_MIN_TR_US` (1000 мкс) ⇒
   `FocSlipPolicy_IsMeasuredTr()` = false ⇒ `ComputeDelta()` = 0 ⇒ θe только с
   энкодера. Поведение fail-safe и корректное, но в телеметрии не видно, что
   slip-модель выключена. Нужен флаг в `@FOC`-строке.
2. **Молчаливая подмена Lσ.** В `FOC_SetMotorParams` при `lsigma < l_uh/10`
   (`src/foc.c:466`, в том числе при отрицательном `Ls − Lm²/Lr`) `foc_lsigma_uH`
   остаётся равным Ls. Мусор не пропускается, но регулятор и observer получают
   завышенную на порядок индуктивность — тоже без индикации.
3. **Двойная инициализация observer'а при первом старте:** `FOC_Init()`
   (`src/foc.c:562`) и `BEMF_Init()` ниже (`src/foc.c:572`) — сначала по дефолтам,
   потом по текущим значениям. Не баг, чистка отдельно.

Пункты 1-2 — наблюдаемость, не safety. Приоритет ниже, но именно молчаливые
деградации стали причиной того, что этот дефект обсуждался два раунда.

## 9. Ревизия 2 (14.09.2026): приоритет admission — Rs/Ls раньше карты

**Причина.** На стенде гейт оказался недостижим: `FOC_Start()` проверял готовность
карты (`src/foc.c:542`, код `-2`) раньше значений Rs/Ls (`src/foc.c:561`, код `-6`).
При отсутствующей карте команда `1` возвращала `-2` при любых параметрах, поэтому
стендовые T1–T4 не могли подтвердить interlock (подтверждено логом стенда 23.08:
`1 → @FOC:START:FAIL:rc=-2`).

**Решение — новый контракт приоритета admission:**

1. clock/fault → `-1`
2. **Rs/Ls sanity (по значению) → `-6`**
3. готовность карты реконструкции → `-2`
4. startup-контекст карты → `-2`
5. калибровка оффсетов → `-3`
6. ADC arm → `-4`
7. `PWM_Enable` → `-5`

**Наблюдаемая семантика.** При одновременно невалидных Rs/Ls и отсутствующей карте
причиной отказа является `-6`: параметрный sanity-gate имеет более высокий
admission-приоритет. На «чистой» плате без `mp=` отказ тоже `-6` — прямое следствие
инварианта §4 (дефолт `FOC_DEFAULT_L_UH=100` намеренно вне окна валидности).

**Изменённые файлы.**

- `src/foc.c` — перенос гейта Rs/Ls выше гейтов карты; уточнён текст подсказки при
  `-2` (прежняя ссылка на `ch/chu/chv/chw` устарела: это команды автоподстройки, карту
  они не грузят).
- `tests/foc_start_gate_test.c` — матрица приоритета (A0/A/B/C/D/E).

**Не изменяется:** fail-closed, отсутствие побочных эффектов при отказе (PWM/ADC/CEN/MOE
выключены, `FOC_Init()` не вызывается — проверяется `FOC_TestIsInitialized()`),
инвариант дефолта из §4, поведение `mp=`/`mpapply`.

**Матрица хостового теста:**

| Состояние | Rs/Ls | Карта | Ожидание |
| --- | --- | --- | --- |
| A0 | дефолт (намеренно невалиден) | отсутствует | `-6` |
| A | invalid | отсутствует | `-6` |
| B | valid | отсутствует | `-2` |
| C | invalid | готова | `-6` |
| D | valid | готова | проходит дальше по цепочке |
| E | гранично valid (`==min`/`==max`) | готова | не `-6` |

Состояния A0 и B вместе доказывают, что порядок гейтов — намеренный контракт, а не
побочный эффект расположения строк.

**Стендовое следствие.** T1–T4 выполняются на обычной production-сборке: без карты и
без возможности открыть PWM (`PWM_Enable` → `-5` даже при случайно валидных
параметрах). Протокол сессии — `C:\campaign_raw\tz1_t1t4_pkg_20260914\SESSION_TZ1_T1_T4_PROTOCOL.md`
(после ревизии 2 применим без предварительной загрузки карты).
