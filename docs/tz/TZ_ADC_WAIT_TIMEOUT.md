# ТЗ: ADC — ожидания флагов не сообщают таймаут (`adc_wait_set` / `adc_wait_clear`)

**Источник:** найдено 2026-10-15 при разборе host-тестов `adc_regular_injected_guard_test` и
`adc_sequence_monotonic_test` (коммит `6d08279`): предустановка `ADEN` в тесте давала не
обещанный в комментарии отказ, а PASS — разбор привёл в `src/adc.c`. Дефект внесён вместе с
dual-injected реворком `8aad003` (2026-08-14), то есть живёт в `main` с 14.08.

## Объект

`src/adc.c` — две статические функции опроса регистра (единственные в проекте с этим шаблоном):

```c
static int adc_wait_set(volatile uint32_t *reg, uint32_t mask)     /* adc.c:62-67 */
{
    uint32_t n = ADC_WAIT_CYCLES;
    while (((*reg & mask) == 0u) && (n-- != 0u)) { }
    return (n == 0u) ? -1 : 0;
}

static int adc_wait_clear(volatile uint32_t *reg, uint32_t mask)   /* adc.c:69-74 */
{
    uint32_t n = ADC_WAIT_CYCLES;
    while (((*reg & mask) != 0u) && (n-- != 0u)) { }
    return (n == 0u) ? -1 : 0;
}
```

## Проблема (подтверждено)

**Обе функции не могут вернуть `-1`: таймаут сообщается как успех.** При `n == 0` выражение
`n--` даёт ложь — по этой ветви цикл и выходит, — а сам `n` после постдекремента становится
`0xFFFFFFFF`. Поэтому проверка `n == 0u`, которая и должна была отличать «флаг не дождались»,
не истинна никогда, и функция возвращает `0`.

Воспроизведение (host, gcc, `-DADC_HOST_TEST`, мок `tests/mocks_adc`):

1. `ADC_Init()` на моке, где `ADCAL` выставлен и никем не снимается, возвращает **0**, а `CR`
   после него равен `0x90000000` — бит `ADCAL` так и не снят. То есть «калибровка завершилась» —
   ложное утверждение.
2. Сборка **закоммиченной** ревизии обоих ADC-тестов с предустановленным `ADEN` (то есть с тем
   самым состоянием, которое комментарий в тестах объявлял фатальным) даёт `PASS` в обоих.

Последствия на железе — молчаливый успех вместо отказа:

| Строка | Чего ждём | Что происходит сейчас |
|---|---|---|
| 155 | `ADDIS` снял `ADEN` | считает, что ADC выключен |
| 167 | `ADCAL` снят (калибровка) | считает, что калибровка прошла |
| 174 | `ADRDY` выставлен (включение) | считает, что ADC готов |
| 221 | `ADSTP` снят | результат отброшен (`(void)`) |
| 344 | `JADSTP` снят | `adc_stats.timeout_count++` — счётчик мёртв, он ждёт `-1` |

На здоровой плате ни один из этих путей не выполняется (флаги успевают к первому опросу),
поэтому дефект невидим и в прогонах не проявлялся: он срабатывает ровно тогда, когда нужен.

Fail-closed путь на отказ ADC в прошивке **уже написан и сегодня недостижим**: `main.c:688` при
`ADC_Init() != 0` ставит `g_clock_fail = 1` и печатает `ADC INIT FAIL: power stage locked`, а
`g_clock_fail` запрещает силовую часть (`src/pwm.c:216`, `src/pwm.c:680`, `src/foc.c:559`).

## Требования

1. Обе функции обязаны возвращать `-1` при исчерпании счётчика и `0` — только при наблюдённом
   изменении флага. Форма записи — на выбор исполнителя, например:

   ```c
   uint32_t n = ADC_WAIT_CYCLES;
   while (((*reg & mask) != 0u) && (n != 0u)) { --n; }
   return (n == 0u) ? -1 : 0;
   ```

2. Набор и порядок вызовов не меняются: те же пять мест, никаких новых проверок в `ADC_Init`.

3. `ADC_WAIT_CYCLES` (`src/adc.h:31-33`) в этом ТЗ не трогать. Запас там большой: счётчик 10⁶
   итераций при 170 МГц — это ориентировочно **24…35 мс** (допущение 4–6 тактов на итерацию
   цикла опроса), тогда как ADC-клок 42.5 МГц успевает за это время отсчитать ~10⁶ тактов.
   Менять предел — отдельный вопрос с расчётом, не здесь.

4. Вызывающих не «глушить»: если `ADC_Init()`/`ADC_InjectedInit()` теперь возвращают `-1`,
   верное поведение — уже написанное (`g_clock_fail = 1`, силовая часть запрещена). Никаких
   «повторить и продолжить» и никаких ретраев внутри ожиданий.

5. **Host-хук под `#ifdef ADC_HOST_TEST` — обязателен, иначе правку нельзя проверить.** Мок
   регистров не моделирует квитирование (`ADDIS` не снимает `ADEN`, `ADCAL` не снимается сам,
   `ADRDY` не выставляется), поэтому после исправления ожиданий **все** существующие ADC-тесты
   начнут получать `-1` от `ADC_Init()` и покраснеют. Требуется:

   - в `src/adc.c` в обоих циклах — вызов хостового хука (например `ADC_HostWaitHook(reg, mask)`)
     под `#ifdef ADC_HOST_TEST`; в production-сборке он пуст (`do { } while (0)`), стоимость —
     ноль;
   - в моке (`tests/mocks_adc/registers.c`) — реализация хука, эмулирующая завершение железа:
     `ADDIS` снимает `ADEN` и `ADDIS`, ожидание `ADCAL` снимает `ADCAL`, ожидание `ADRDY`
     выставляет `ADRDY`; отдельный флаг мока («железо не отвечает») позволяет воспроизвести
     таймаут.

6. **Обязательный тест на таймаут** (`tests/adc_wait_timeout_test.c` либо расширение
   существующего ADC-теста): при моке в режиме «железо не отвечает» `ADC_Init()` (или сами
   функции) даёт `-1`, при нормальном квитировании — `0`. Проверка обратным ходом обязательна:
   **на текущем коде тест красный, на исправленном — зелёный**. Тест, который проходит и без
   правки, приёмке не подлежит.

## Приёмка

- `make` (ARM, `-Wall -Wextra -Werror`) — без предупреждений; размер кода не вырос заметно
  (в production хука нет);
- `make test` (hosted + QEMU + pytest) — ALL PASS, включая существующие ADC-тесты: они
  проходят теперь по моделированному квитированию, а не благодаря дефекту;
- новый тест красный на ревизии **до** правки (отдельный worktree/`git stash`) и зелёный после —
  в отчёт обе вывода;
- `git diff --check` чист; diff ограничен `src/adc.c`, `tests/mocks_adc/**` и новым/расширенным
  тестом;
- `src/pwm.c`, `src/protect.c`, `src/foc.c`, `src/vf*.c`, `.ioc` — не тронуты;
- в отчёте — вывод `git ls-remote origin <ветка>` (см. «Публикация»).

## Публикация

Ветка `ai<N>/adc-wait-timeout` от свежего `main`, **явно опубликована**: `git push -u origin
<ветка>`, в отчёте — вывод `git ls-remote origin <ветка>`; в этом репозитории неопубликованная
ветка приёмке не подлежит. PR открывать не обязательно; при открытии — указать в описании
команду проверки обратным ходом и её результат.

## Ограничения

- `src/adc*` — safety-модуль: только две функции плюс host-хук под `#ifdef`. Без рефакторинга,
  переименований и переноса кода между файлами.
- Порядок инициализации в `main.c` не менять; fail-closed (`g_clock_fail`, `PROTECT`) не
  ослаблять; default-deny (`OEW_MAP_CAPTURE` / `OEW_MAP_L3` / `RELEASE`) не трогать.
- Временные принты — под `#if 0`, перед публикацией убрать.
- Не «чинить» это в тестах (предустановками регистров, обходами): правка теста не заменяет
  правку ожидания.

## Стендовая проверка (после прошивки, пользователь)

Правка не меняет поведение здоровой платы, поэтому проверка — «нет ложных срабатываний»:

1. `make backup`, прошивка, затем `c` → `a` → `sysinfo`.
2. Лог загрузки: `ADC OK, injected OK` — калибровка и `ADRDY` действительно дождались, ложного
   таймаута нет.
3. `a` → raw I1/I2/Ires ≈ 2048, VBUS ≈ 595 отсч при 60 В; `1` → `FOC started` (силовая часть
   не заблокирована).
4. Если в логе появилось `ADC INIT FAIL: power stage locked`, а `1` отвечает `FOC start blocked:
   clock fail or fault latched` — это сработавший таймаут, то есть правка ужесточила поведение.
   Разбираться как с отказом ADC (питание, клок, регистры), а не «обойти».

## Смежное, что этот ТЗ не закрывает

- Строка 221 (`ADSTP`) отбрасывает результат: после правки есть смысл и её учитывать в
  `adc_stats.timeout_count` — но это отдельное решение, здесь не требуется.
- Мок не моделирует тайминги выборки/преобразования (из этого же класса: предустановка `ADEN`
  в тестах ничего не проверяла) — отдельная задача по моку.
- Host-проверки «main при отказе ADC» (что `g_clock_fail` действительно блокирует `1`)
  отсутствуют; это отдельное ТЗ.
