# Техническое задание для web AI: поиск неисправности чтения VBUS/токов АЦП

## 1. Объект

Проект **OEW** — STM32G474RE (Nucleo-G474RE, MB1367), два инвертора
STEVAL-IPM20B (Inv1/TIM1, Inv2/TIM8), общий DC-link ~60 В от лабораторного БП.

Аналоговые каналы (ADC2, 12-bit, VREF=3.3В):

| Сигнал | Пин MCU | ADC2 канал | Физический источник |
|--------|---------|-----------|---------------------|
| **I1** | PA0 | IN1 | Шунт DC-link Inv1, через ОУ (gain 2.1, смещение 1.65В) |
| **I2** | PA1 | IN2 | Шунт DC-link Inv2, через ОУ (gain 2.1, смещение 1.65В) |
| **Ires** | PA6 | IN3 | Трансформатор тока (CT), нулевой ток OEW |
| **VBUS** | PC4 | IN5 | Делитель 1:125 (R_high, R_low) на плате STEVAL |

Формулы прошивки (`src/adc.c`):
- `I_ma = (raw − offset) * 3300 * 1000000 / (4095 * 63000)` → ~26.1 А при diff=2047 (raw 4095, offset 2048)
- `VBUS_mV = raw * 3300 * 125 / 4095` → ~60000 мВ при raw≈595 (0.48В)

## 2. Симптомы

### 2.1 Прошивка читает VBUS ≈ 0, хотя напряжение физически есть

| Измерение | Значение | Ожидаемое |
|-----------|----------|-----------|
| БП DC-link | 60.0В / 0.00А | 60В |
| Мультиметр: клеммы DC+/DC- на STEVAL | 60.0В | 60В |
| Мультиметр: J2.pin14 (HV bus sense) | 0.48В | 0.48В (60/125) |
| Мультиметр: CN10-34 (Nucleo, = PC4) | 0.48В | 0.48В |
| Прошивка: `a` → `VBUS=` | **2–604 мВ** (raw≈2–6) | ~60000 мВ (raw≈595) |

### 2.2 Прошивка читает I1/I2 ≈ 26 А (насыщение) при нулевом токе

| Измерение | Значение | Ожидаемое |
|-----------|----------|-----------|
| Мультиметр: PA0 (I1) | 1.65В | 1.65В (ноль тока) |
| Мультиметр: PA1 (I2) | 1.65В | 1.65В (ноль тока) |
| Прошивка: `@FOC:I1=` | **26120 мА** (raw≈4095, полная шкала) | ~0 мА (raw≈2048) |

### 2.3 Сброс fault невозможен

- `FAULT=1, FAULT_R=18` (HARDWARE_BREAK) — защёлкнут после включения 60В
  (предположительно: при заряде C-банка просадка → UVLO → SD=0 на долю секунды).
- `f` → `PROTECT_RequestClear()` отклоняет: `VBUS=201мВ < PROTECT_VBUS_MIN_MV(8000)`
  (см. `src/protect.c:185`). Пока АЦП не читает 60В, сброс невозможен.

## 4. Ключевое противоречие — вопрос к AI

Мультиметр показывает **правильные напряжения на пинах разъёмов Nucleo**
(CN10-34 = 0.48В, PA0/PA1 = 1.65В), но АЦП читает **крайние значения**:
raw≈2 на PC4 и raw≈4095 на PA0/PA1.

Это не похоже на «не та формула» и не похоже на «не тот канал» — похоже на то,
что **сигнал физически не доходит от разъёма до вывода MCU** (перемычки
solder bridge SBxx на MB1367), либо АЦП не сконфигурирован вовсе
(нет тактирования / не вызван `ADC_Init` / `PWM_BoardPins_Init`).

**Вопросы AI:**
1. Какие solder bridge'и на Nucleo-G474RE (MB1367, UM2505) отвечают за PA0, PA1, PA6, PC4?
   Нужны номера SBxx и их состояние по умолчанию.
2. Как проверить без осциллографа (только мультиметр и UART), доходит ли сигнал
   до **вывода LQFP-64 MCU**, а не только до разъёма? (прозвонка?)
3. Какие ещё причины дают ровно такой симптом: PA0/PA1 → 4095 (полная шкала),
   PC4 → 2 (почти 0), при корректных напряжениях на разъёмах?
   - Незапаянные SB?
   - GPIO не в analog mode (но код есть — проверить порядок вызовов в main.c)?
   - VREF+/VDDA не подключены?
   - Конфликт с TIM2_CH1 (PA15/энкодер) или отладчиком?
   - АЦП не откалиброван/не запущен?
4. Почему **после подачи 60В** защёлкнулся FAULT_R=18 (HARDWARE_BREAK)?
   Является ли это штатным поведением при заряде C-банка (UVLO → SD кратковременно =0),
   и как правильно «взводить» стенд после этого (порядок включения БП vs логики)?

## 5. План диагностики для AI

AI должен предложить **пошаговую инструкцию**, которую пользователь сможет
выполнить в текущей конфигурации (ПК-1, COM4, make/make flash, мультиметр),
без осциллографа и без изменения safety-логики.

**Уже доступная команда (main.c:614-615):** `a=N` (например `a=200`) включает
поток сырых значений АЦП:

```text
@ADC:I1=4095:I2=4095:Ires=2048:VBUS=2:...
```

- `VBUS` здесь — **сырой raw** (0..4095), не мВ. Если raw≈600 при 0.48В — АЦП
  читает канал корректно, и проблема в обработке/калибровке. Если raw≈2 —
  сигнал физически не доходит до входа MCU.
- `I1`/`I2` — raw каналов тока (ожидаемо ~2048 при нуле, ~4095 = насыщение).

Ожидаемые шаги (уточнить/дополнить):
1. Выполнить `a=200` и зафиксировать raw-значения 4 каналов — определить,
   доходят ли сигналы до АЦП вообще.
2. Проверить перемычки SBxx на MB1367 для PA0/PA1/PA6/PC4 (номера из UM2505).
3. Прозвонить CN10-34 → вывод PC4 MCU (ножка LQFP-64).
4. Прозвонить CN7/CN9 → выводы PA0/PA1/PA6.
5. Проверить порядок инициализации в `main.c`: `PWM_BoardPins_Init()` (внутри
   `PWM_Init()`) до `ADC_Init()`/`ADC_InjectedInit()`, и что обе вызываются
   (иначе GPIO могут остаться в reset state = analog, но без тактирования
   порта — см. RM0440 GPIO reset state).
6. Проверить `GPIOC->MODER` / `GPIOA->MODER` через debug-команду (dump),
   убедиться, что биты MODER=11 установлены в рантайме (а не только в коде).
7. Проверить тактирование: `RCC->AHB2ENR` (GPIOA/CEN, ADC12EN) — выставлены ли биты.

## 6. Ограничения и безопасность

- **Питание на стенде сейчас**: БП 60В / 0.00А, PWM off (MOE=0), мосты high-Z.
  Низковольтная логика 3.3В/15В подана. Работы безопасны.
- **НЕ подавать PWM** (`1`, `ch`, `mapcap*`) до устранения неисправности АЦП:
  прошивка без достоверного VBUS/токов не может безопасно управлять мостом.
- Код на **CMSIS only**, HAL запрещён (AGENTS.md).
- Любое изменение: `make` → `make flash`, затем повторная проверка.
- Не менять safety-модули (`protect.c`, `pwm.c`, `.ioc`) без отдельного ТЗ.
- Временные диагностические принты — допустимы, обрамлять `#ifdef`/`#if 0`
  и убирать после диагностики.

## 7. Ожидаемый результат

1. **Корневая причина** неисправности чтения АЦП (перемычка/порядок инициализации/
   тактирование/иное) с доказательствами (прозвонка, readout регистров).
2. **Исправление** (diff или пошаговая инструкция): запаять SB / поправить main.c /
   добавить missing init.
3. **Методика повторного взвода стенда** после FAULT_R=18 без отключения БП
   (корректный порядок: сброс `f` после того, как VBUS читается корректно).
4. После исправления — прошивка должна показывать:
   - `VBUS ≈ 60000 мВ` при 60В,
   - `I1≈0, I2≈0` при нулевом токе (raw≈2048, offset калибруется),
   - `f` → FAULT сброшен, `em_stop1=1:em_stop2=1`.
