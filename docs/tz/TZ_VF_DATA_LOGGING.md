# ТЗ: Онлайн-сбор данных со всех датчиков + логического анализатора в режиме V/f

## 1. Цель

Организовать **единый онлайн-лог** (потоковая запись в реальном времени, без
постобработки вручную) всех доступных источников данных **одновременно** во
время работы **V/f-режима** (`VFC_*`, `src/vf_control.c`), чтобы отлаживать
алгоритм управления двигателем (ПИ скорости, slip-модель, V/f-кривую,
переходные процессы разгона/торможения) по единой синхронизированной
временной шкале, а не сверяя вручную несколько разрозненных источников.

**Не путать** с текущим набором отдельных ad-hoc команд (`a?`, `vf?`, `enc`,
`p?`) — они дают снимок состояния по запросу, но не непрерывный
синхронизированный лог с привязкой ко времени и к отдельному прогону.

## 2. Существующие источники данных (инвентаризация)

### 2.1. UART-телеметрия с MCU (уже реализовано, `main.c`)

| Источник | Команда/событие | Поля | Частота |
|---|---|---|---|
| V/f контроллер | `vf?` (по запросу) | `target, meas, fe, fslip, vmag` | ручной опрос |
| Энкодер AS5048A (PWM) | `enc` (по запросу) | `angle, speed, period_us, pulse_us, err` | ручной опрос |
| АЦП (токи, шина) | `a` / `a=N` (стрим) | `I1, I2, Ires, VBUS` | до 20 Гц (`a=50`) |
| PWM регистры | `p?`, `dump`, `pdump` | сырые регистры TIM1/TIM8 | ручной опрос |
| Fault/protect | неявно через `PROTECT_IsFault()` в ответах на `vf=` | булево + причина | по событию |

**Проблема:** данные приходят из **разных команд, в разное время, без общей
метки времени** — сопоставить `@VF:...` и `@ADC:...` и `@ENC:...` друг с
другом на конкретный момент физического процесса невозможно.

### 2.2. Логический анализатор (sigrok, `nucleo_debug_tool.py`)

- Класс `SaleaeHelper` — обёртка над `sigrok-cli`, снимает **цифровые**
  каналы (сейчас настроено на HIN/LIN линии инверторов TIM1/TIM8,
  `PWMTab.PROBE_MAP`) и умеет разово захватывать окно `duration_s`.
- Сейчас используется **изолированно** от UART-телеметрии — нет привязки
  захвата к моменту старта V/f и нет единой временной оси с УАРТ-данными.

### 2.3. Данные, которых пока нет в телеметрии, но нужны для отладки V/f

- **Заданная скважность PWM** (`d_u, d_v, d_w` из `vf_control.c:157-159`) —
  сейчас нигде не публикуется по UART, есть только конечные регистры через
  `p?`/`dump`, которые не привязаны к V/f-циклу.
- **`theta_elec`** (текущий электрический угол, phase accumulator) — полезен
  для сверки с логическим анализатором (для поиска рассинхронизации фаз).
- **Код причины fault** (`PROTECT_GetFaultReason()`, `src/protect.c`) — сейчас
  видно только сам факт останова, не причину, в момент срабатывания.

## 3. Требования к решению

### 3.1. Прошивка (STM32, C)

1. **Один объединённый телеметрический пакет** для V/f-сессии — новая
   команда/режим стриминга, например `vflog=<period_ms>` (по аналогии с
   `a=<N>`), который на каждый тик TIM6 (или с указанным периодом) шлёт
   **одну строку**, содержащую все нужные поля одновременно:

   ```
   @VFLOG:t=<sys_tick_ms>:target=<rpm>:meas=<rpm>:fe=<Hz>:fslip=<Hz>:
          vmag=<pct>:theta=<u32>:du=<pct>:dv=<pct>:dw=<pct>:
          i1=<raw>:i2=<raw>:ires=<raw>:vbus=<raw>:
          enc_angle=<0..16383>:enc_speed=<rpm>:enc_err=<mask>:
          fault=<0|reason_code>
   ```

   Обязательно — **общее поле `t`** (мс от `sys_tick_ms`, уже существует в
   `main.c`) для последующей синхронизации с логами GUI и с sigrok-захватом.

2. **Не создавать новую ISR** — переиспользовать существующий `TIM6_DAC_IRQHandler`
   (1 кГц, уже вызывает `ENC_Update()`+`VFC_Update()`+`ADC_StartConversion()`)
   и добавить накопление/публикацию пакета там же либо через отдельный
   счётчик-делитель частоты (например, публиковать раз в 10 тиков = 100 Гц,
   чтобы не залить UART при 115200 бод).

3. **Не блокировать control loop — ОБЯЗАТЕЛЬНО использовать
   `UART_TrySendTelemetry()`** (не `UART_SendTelemetry()`) для публикации
   `vflog` из `TIM6_DAC_IRQHandler`. Проверка показала: обычный
   `UART_SendStr`/`UART_SendTelemetry` при заполнении кольцевого буфера
   делает `while(next==tx_tail){}`, полагаясь на то, что `USART2_IRQHandler`
   параллельно освобождает место — но `TIM6_DAC_IRQn` (приоритет 1) не
   может быть вытеснен `USART2_IRQn` (приоритет 2, ниже), т.к. на Cortex-M
   ISR с более высоким приоритетом не прерывается ISR с более низким, пока
   выполняется. Это классический priority-inversion **deadlock** (не
   задержка), если буфер переполнится в момент публикации из TIM6 —
   например, при параллельном ручном вызове `a?`/`enc`/`p?` во время
   активного `vflog`-стрима. Неблокирующие `UART_TrySendStr()` /
   `UART_TrySendTelemetry()` (см. `src/uart.c`/`src/uart.h`) уже
   реализованы — при нехватке места отбрасывают пакет целиком (не
   частично) и инкрементируют `UART_GetDroppedCount()`, без блокировки.
   Публикатор `vflog` обязан использовать именно их.

4. **Публикация fault-причины**: добавить `PROTECT_GetFaultReason()` в пакет
   (уже существует в `protect.c`, просто не публиковался раньше).

5. **Явный старт/стоп лога синхронно со стартом V/f**: например, при
   `vf=<rpm>` (V/f start) автоматически включать `vflog`, при `vf=0`
   (V/f stop) — выключать, чтобы GUI не должен был дергать 2 отдельные
   команды и не терять первые миллисекунды переходного процесса разгона.

### 3.2. GUI (`nucleo_debug_tool.py` / `vf_panel.py`)

1. **Единый CSV-лог сессии** — при нажатии "Start V/f" в `VfPanel`:
   - создаётся файл `logs/vf_session_<timestamp>.csv`;
   - каждая полученная строка `@VFLOG:...` парсится и дописывается как
     строка CSV (используя существующий `TLM_PREFIX_RE`/`TLM_KV_RE`);
   - параллельно (если `SaleaeHelper.available`) **автоматически запускается**
     захват логического анализатора на заданную длительность (например,
     на время разгонной рампы `VFC_RAMP_TIME_MS` + запас), с сохранением
     `digital.csv` в ту же папку сессии — единый каталог с общим timestamp
     в имени, чтобы визуально сопоставить файлы без сложной синхронизации
     по абсолютному времени ПК (учитывая, что UART-`t` и sigrok-время не
     имеют общего нуля — см. риски ниже).

2. **Живой график в реальном времени** (опционально, если не будет
   избыточной нагрузки на Tkinter event loop) — минимум: обновляемые
   числовые лейблы (уже есть `vf_status_label`, `enc_angle_label`,
   `enc_speed_label` в `vf_panel.py`), максимум — добавить простой
   line-plot (matplotlib embed или Tkinter Canvas) скорости/задания/тока
   от времени `t`, обновляемый по мере прихода `@VFLOG` строк.

3. **Кнопка "Stop & Save"** — принудительная остановка лога и явное
   сохранение CSV с текущим содержимым буфера (на случай, если V/f
   остановлен по fault, а не штатной командой).

### 3.3. Формат хранения на диске

```
logs/
  vf_session_20260809_221300/
    telemetry.csv       # t_ms,target,meas,fe,fslip,vmag,theta,du,dv,dw,i1,i2,ires,vbus,enc_angle,enc_speed,enc_err,fault
    digital.csv         # sigrok-формат (как сейчас снимает SaleaeHelper)
    meta.json           # rpm target, boost/rated params, timestamp старта, длительность
```

## 4. Риски и открытые вопросы

1. **Нагрузка на UART при 100+ Гц потоке** — при 115200 бод и длинной строке
   `@VFLOG` (потенциально ~120+ символов) реальный лимит частоты стрима
   нужно посчитать (`115200/10 бит ≈ 11.5 KB/s` → строка 120 байт →
   максимум ~95 Гц без потерь) — **нужно явно ограничить период** (например,
   не чаще 50 Гц) либо сократить набор полей для стрим-режима.
2. ~~Нет общей временной привязки UART↔sigrok~~ — **устранено аппаратным
   триггером**: `PB6` (освобождён после удаления SPI2 CS) подаёт фронт ровно
   в момент `VFC_Start()` (`TRIG_High()` в `main.c`, команда `vf=<rpm>`),
   одновременно с этим MCU публикует `sys_tick_ms` в `@TRIG:tick=...`.
   GUI (`vf_panel.py`) требует физического подключения щупа `sigrok` от
   `PB6` к каналу `TRIGGER_SIGROK_CHANNEL` (по умолчанию `D7`), находит
   фронт в захваченном `digital.csv` и пишет точную привязку в
   `meta.json` → `sync`: `trigger_tick_ms` + `trigger_edge_ns` + формулу
   пересчёта `sigrok_time_ns(row) = trigger_edge_ns + (row.t_ms - trigger_tick_ms) * 1e6`.
   Точность ограничена периодом `SysTick` (1мс) и разрешением `sigrok`
   (при 8МГц — 125нс), что кратно точнее приблизительной USB/UART-оценки.
3. ~~Блокирующий UART TX в ISR~~ — **устранено**: добавлены
   `UART_TrySendStr()`/`UART_TrySendTelemetry()` (см. `src/uart.c`) —
   неблокирующие, отбрасывают пакет целиком при нехватке места вместо
   `while(){}`-дедлока. Публикатор `vflog` обязан использовать их, а не
   обычные `UART_SendStr`/`UART_SendTelemetry`.
4. **Формат `@VFLOG` ломает существующий парсер построчно по префиксам**
   (`TLM_PREFIX_RE`) в `nucleo_debug_tool.py:1559-1568` — нужно добавить
   обработчик `elif p=="VFLOG": ...` без нарушения существующих `VF`/`ENC`/
   `ADC`/`PWM` веток (они могут работать параллельно для отдельных
   ручных команд).

## 5. Объём работ (оценка, для дальнейшей декомпозиции на задачи)

1. **Прошивка**: новая команда `vflog=<period_ms>` + буферизация/публикация
   объединённого пакета из `TIM6_DAC_IRQHandler` + `PROTECT_GetFaultReason()`
   в телеметрию + (если потребуется) неблокирующий UART TX.
2. **GUI**: обработчик `@VFLOG` → запись CSV сессии, авто-старт/стоп
   логического анализатора синхронно с `vf=`/`vf=0`, папка сессии с
   `meta.json`.
3. **(Опционально) Живой график** скорости/тока в `VfPanel`.
4. **Тест**: запустить `vf=1500`, убедиться, что `logs/vf_session_.../telemetry.csv`
   содержит непрерывный ряд без пропусков по `t_ms` и без визуальных
   провисаний UI, сверить пару точек с ручными `vf?`/`enc`/`a` командами.

## 6. Не входит в объём (явно вне ТЗ)

- Точная (суб-миллисекундная) аппаратная синхронизация UART и sigrok —
  только по явному запросу, требует отдельного проектирования (GPIO-триггер).
- Запись в режиме FOC (`foc.c`) — данное ТЗ ограничено только V/f-режимом
  (`vf_control.c`/`VFC_*`), как указано в постановке задачи.
