# ACCEPTANCE_LESSONS.md — уроки приёмки пакетов (версионируемые)

Зачем этот файл: уроки приёмки раньше жили в переписке и в скилле
`oew-package-acceptance`, который лежит **вне репозитория и не версионируется
вместе с кодом** (проверено 15.09.2026: скилла нет ни в репозитории, ни в
рабочем профиле ПК). Урок, не закреплённый в артефакте, теряется молча —
поэтому §22–§24 продублированы здесь.

Правило: правка, вызванная уроком, и сам урок — в одном коммите/пакете.
Нумерация §22+ продолжает сквозную нумерацию скилла.

## §22 Парсер кампании молча подставляет пороговые значения

`tools/map_scope_ingest.py`:

* `BOAR_MARGIN = 110` — это **порог гейта** `margin_ticks >= 110`;
* `BOAR_BLANKING = 15` — окно выборки ADC;
* `parse_scope_csv()` читает их как умолчания: `num("margin_ticks", BOAR_MARGIN)`,
  `num("blanking_ticks", BOAR_BLANKING)`, `num("scope_qualified", 0)`.

Следствие: пустая ячейка `margin_ticks` превращается в **ровно 110** и гейт
проходит **без измерения**.

Уточнение (проверено на пакете TZ-02 P0/P1, 15.09.2026): при пустых
`ref_u_mv`/`ref_v_mv` парсер падает раньше (`ref_u/v_mv обязательны`) — «дыра»
материализуется, когда `ref_*` заполнены, а `margin_ticks` пуст.

Правило: верификатор обязан требовать непустые заявленные поля **до** вызова
штатного парсера. Реализация — `p0p1_verify.py::check_no_blank_fields()`
(обязательные: `ref_u_mv`, `ref_v_mv`, `margin_ticks`, `blanking_ticks`,
`scope_qualified`).

Живая проверка: пробный CSV (ref_* заполнены, `scope_qualified=1`,
`margin_ticks` пусто) → штатный парсер отдаёт `margin_ticks=110`;
`check_no_blank_fields()` → REJECT; тот же файл с `110/15/1` → OK.

## §23 «Регион» = строка карты, а не строка файла

* `region_row(r) = (r // 2, r % 2)` (`tools/map_scope_ingest.py:139`):
  region 0 → (sector 0, window 0), region 7 → (sector 3, window 1).
* Grid-раскладка: `logs/region_<r>_<p>.log` + `scope/scope_region_<r>_<p>.csv`,
  `p ∈ 0..3`, по 8 записей на файл (`GRID_POINT_RECORDS = 8`).
* Привязка лога к строке — только через `expected_ccr(sector, window, point)`:
  полный CCR-вектор в каждой записи обязан совпасть, иначе REJECT
  («лог не того региона?»). Подстановка лога соседнего региона ловится именно так.
* `build_campaign` требует **все 12 регионов** → для 1–2 строк (P0/P1) нужен
  scoped-верификатор: `p0p1_verify.py` работает по allow-list `REGIONS = (0, 7)`.

## §24 Составной отчёт; «заявленный SHA» ≠ provenance

* Формальные гейты печатаются и пишутся в отчёт **отдельно** от `PENDING`/`BLOCKED`
  (независимость референса, численное выравнивание, G3 — не покрываются скриптом).
* «Заявленный sha == ожидаемый» — это сравнение **значений из манифеста**;
  доказательством прошивки оно не является. Факт прошивки = дамп платы
  (`STM32_Programmer_CLI`, шаг 4 §6 протокола).
* Ошибки ловятся широким `except Exception` с коротким сообщением (fail-closed,
  без traceback) — `p0p1_verify.py:176`, `:198`; `exit 0` означает только
  «формальные гейты ingest пройдены».

## §25 Рецепты и факты, проверенные 15.09.2026

### 25.1 Provenance образа — пересборкой из git-объектов, а не сверкой хешей

```bash
git archive --format=tar -o /tmp/p.tar <commit> && tar -xf /tmp/p.tar -C /tmp/p
cd /tmp/p && make clean && make EXTRA_CFLAGS="<из SOURCE_COMMIT.txt>"
sha256sum build/firmware.bin        # сверить с SHA256.txt пакета
```

Проверено на TZ-02 P0/P1: `b39b3b6` + флаги из `SOURCE_COMMIT.txt` →
`47075264a1c2fa7a69910e5d83af56732e6ead169f6832e39ee1cc4c3427f5cc`,
79 488 Б, text/data/bss = 78964/516/13628 — совпало с пакетом. Сборка дала
байт-в-байт тот же образ **даже на GCC 14.3.1** (пакет заявлен собранным 13.2.rel1),
т.е. проверка устойчива к версии тулчейна. Пересборка — дешёвый способ заменить
«заявленный sha» реальным доказательством.

### 25.2 Устаревший дубликат инструмента опаснее, чем кажется

Перед сессией сверять константы `BOAR_ADC_SIG` / `BOAR_CAL_SIG` в **каждой**
копии ingest с `templates/firmware_manifest.json` и `P0_CHECKLIST.md`.
Найдено 15.09.2026: копия `мотор анализ/manifest_gen_sources/map_scope_ingest.py`
содержала placeholder-сигнатуры `0x13572468`/`0x24681357` вместо стендовых
`0x26B9B97B`/`0x13552B12` → сверка `pdump` по ней дала бы ложный FAIL.
Дубликат переименован в `map_scope_ingest.py.STALE-0x13572468-DO-NOT-USE`.
Загружается всегда `<repo>/tools/map_scope_ingest.py`.

### 25.3 «Зелёный exit 0» нельзя принимать без негативного теста

Минимальный smoke-набор верификатора:

1. нет свидетельств → REJECT + exit 1 (fail-closed);
2. пустой шаблон калибровки (`vcc_mv: 0`) → REJECT;
3. лог региона 0 в слоте региона 7 → REJECT («лог не того региона?»);
4. пустой `margin_ticks` при заполненных `ref_*` и `scope_qualified=1` → REJECT (§22);
5. полный синтетический набор (8 логов + 8 CSV) → exit 0 и `verification_report.json`
   с sha256 всех 16 файлов свидетельств.

### 25.4 Манифест пакета не хеширует сам себя

`PACKET_MANIFEST.txt` не содержит собственной строки — это ожидаемо, а не дефект.
Внешний якорь целостности — отдельно сообщённый sha256 ключевых файлов
(`PACKET_README.md`, `p0p1_verify.py`); при приёмке сверять и его.

### 25.5 Сигнатура калибровки воспроизводится только ПОСЛЕ калибровки

`cap_current_calibration_signature()` (`src/map_capture_port.c:146`) включает в CRC
флаг `ADC_OffsetsAreValid()`. Сразу после flash+reset оффсеты невалидны
(`a?` → `offset_i1=0`) → живой `ccs=0xABE94C77`; после `c`
(`@ADC:CAL:offset_i1=2040:offset_i2=2069`) → `ccs=0x13552B12`, т.е. значение
ingest/чеклиста. Проверено 15.09.2026 на ПК-3.

Правило: перед сверкой `acs`/`ccs` из `@MAP:IDENTITY` убедиться, что оффсеты
откалиброваны (`a?` → `offset_i1 != 0`); иначе расхождение — артефакт состояния,
а не дефект, и объявлять по нему BLOCKED нельзя.

### 25.6 Десятичные константы в шаблонах проверять пересчётом в hex

`p0p1_verify.py` сверяет только `flashed_image_sha256`, поэтому числовые поля
шаблонов могут врать и **пройти формальные гейты**. Найдено 15.09.2026
в `templates/firmware_manifest.json` пакета TZ-02 P0/P1:

| поле шаблона | в шаблоне | ожидается (hex платы/ingest) |
|---|---|---|
| `adc_trigger_id` | `1244345137` = `0x4A2B3331` | `0x4F455731` (1329944369) |
| `adc_config_signature` | `649837947` = `0x26BBBD7B` | `0x26B9B97B` (649705851) |
| `current_calibration_signature` | `324104978` = `0x13517312` | `0x13552B12` (324348690) |

`P0_CHECKLIST.md` (hex) был верен, живая плата совпала с ingest. Правило: перед
сессией пересчитывать десятичные поля шаблонов в hex и сверять с живым
`@MAP:IDENTITY`; расхождение = дефект шаблона → перевыпуск манифеста пакета.

### 25.7 Idle-телеметрия `@FOC` не является измерением тока

`@FOC:I1/I2` печатаются из `ADC_GetLatestFrame().idc1_ma` — последнего
зафиксированного injected-кадра. Пока цепочка не armed, кадры не обновляются
(`@ADUMP … JDR1=JDR2=JDR3=JDR4=0`), а при нулевых оффсетах выводится
`raw × 12.79 мА/код` (`calc_dc_shunt_ma`, `src/adc.c:71`): наблюдалось
`I1=26120:I2=26439` мА при разряженном звене (0.5 В) и mid-scale кодах 2042/2067.

Правило: нулевой/рабочий ток проверять в armed-состоянии по `@MC:REC`
(`raw_i1`/`i1`), как и требует `check_evidence`; idle-строку `@FOC` в evidence
P0/P1 не подставлять.

### 25.8 KCL-гейт вырождается, если `ref_w_mv` пуст

`parse_scope_csv` при пустой ячейке `ref_w_mv` выводит `ref_w = -(ref_u + ref_v)`
(`tools/map_scope_ingest.py:240`). Тогда проверка «KCL по `ref_u/ref_v/ref_w`»
(`check_evidence`) выполняется **тождественно** и не может поймать сдвиг нуля любого
из двух измеренных каналов (проверено 15.09.2026: канал V дал `v0 = vcc/2 + 105 мВ`,
т.е. +1.05 А смещения нуля, при полностью зелёных формальных гейтах).

Правило: при пустом `ref_w_mv` относиться к KCL-гейту как к арифметике, а не как к
доказательству; качество независимого референса держится на ручной проверке
независимости/масштаба (шаги 5 и 7 §6) и на сравнении с ожидаемыми токами.
Третий канал (или явный `ref_w_mv`) — единственный способ сделать KCL проверяемым.

### 25.9 Защёлкнутый hardware break не снимается при разряженном DC-link

`PROTECT_RequestClear()` (`src/protect.c:175-192`) возвращает
`PROTECT_CLEAR_VALUES_UNSAFE` (rc=4, «fault NOT cleared: Vbus/current still out of
range»), если SD линии не высокие, **или** `Vbus` вне `PROTECT_VBUS_MIN_MV (8000 мВ) …
PROTECT_VBUS_MAX_MV (350000 мВ)`, **или** `|I| > PROTECT_I_MAX_MA/2 (6000 мА)`,
**или** на момент commit есть незакрытый `BIF/B2IF`.

Проверено 15.09.2026 на ПК-3: при `em_stop1/2 = 1` (SD высокие) и токе ≈ 0, но
`Vbus = 3122 мВ` команда `f` дважды вернула `@FAULT:CLEAR:STATUS=4`. То есть
«не снимается fault» ≠ «неисправность»: на разряженном стенде снять латч **нельзя
по устройству защиты**.

Правила:

* снятие латча — только при DC-link ≥ 8 В (с токоограничением), либо сбросом MCU
  (латч живёт в RAM); сброс **не заменяет** классификацию события;
* событие break классифицируется по матрице §7
  `docs/templates/grid_campaign_boar/README_BOAR_LOW_VOLTAGE_BRINGUP_PC3.md`
  (`sd=0,0` в `@BRK` ⇒ «общая питающая цепь либо одновременная защита» ⇒ BLOCKED);
* снапшот `@BRK` хранит **первый** break до explicit `breakdiag reset`
  (`TZ_FIRST_BREAK_DIAGNOSTICS.md` §2.5) — до разбора события его сбрасывать нельзя,
  это единственная улика (в нём же `src=TIM1|TIM8` и физическое состояние SD1/SD2 в ISR).

### 25.10 `mapcap build` не запускает burst — у точки другой порядок команд

`mapcap build=<id>` (`main.c:314`) требует **уже завершённого захвата**: при
`state != MAP_CAPTURE_COMPLETE`, `terminal_status != OK` или `records_available == 0`
он отвечает `@MAP:BUILD:BLOCKED:CAPTURE_STATE=…:TERM=…:AVAILABLE=…` и выходит. Это шаг
построения *артефакта карты* (MapBuilder/MapCandidate), а не измерение.
Burst запускают `mcarm=<id>` (`MapCapture_Arm`, `src/map_capture.c:150`) и
`mapcap run` (`MapCapture_Run`, `src/map_capture.c:186`).

Правильный порядок точки (совпадает с утверждённым runbook
`docs/templates/grid_campaign_boar/README_BOAR_CAPTURE_PC3.md` §3 и `RUNBOOK_60V_PC3.md` §5):

```text
mcarm=<id>        # arm: SD high, нет fault, оффсеты валидны, control paths inactive
mapcap run        # burst: 8 импульсов (ЭНЕРГИРОВАННЫЙ шаг)
mapcap drain      # 8× @MC:REC + @MC:DRAIN:records=8
mapcap status     # COMPLETE, detail=0
breakdiag         # valid=0 или документированный transient
p?                # CCER=0, MOE=0
```

Найдено 15.09.2026: сессионный скрипт пакета TZ-02 P0/P1 (`p0_p1_session.py`, режим
`region=`) посылает `mapcap build` → `mapcap status` → `mapcap drain`, то есть **без
`mcarm` и без `mapcap run`**. На этом firmware такой прогон даёт
`@MAP:BUILD:BLOCKED:CAPTURE_STATE=0` и `@MC:DRAIN:records=0`, а логи не проходят
собственный гейт пакета (нужно ровно 8 записей). Fail-closed срабатывает корректно
(скрипт печатает REJECT по сводке drain), но **сессию по этому скрипту выполнить нельзя**:
нужен либо перевыпуск пакета, либо явно задокументированная замена последовательности.

Правило: перед сессией сверять порядок CLI-команд с runbook, а не с формулировкой в
README пакета; состояние захвата проверять через `mapcap status` (должно быть
`COMPLETE` **после** `mapcap run`).
