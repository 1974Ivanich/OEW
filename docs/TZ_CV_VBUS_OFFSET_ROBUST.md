# ТЗ: робастная калибровка смещения VBUS (`cv`) на обесточенной шине

Ветка для исполнения: **новая** `ai<N>/cv-robust-vbus-offset` от свежего
`origin/main`. Пакет = одно ТЗ (AGENTS.md). База правок: `src/adc.{c,h}`,
`src/cli.c`, `tests/*`, `docs/`. `src/adc.c` — safety-модуль: правки допустимы
исключительно в объёме этого ТЗ (это ТЗ и есть явное разрешение).

Область пересекается с `docs/TZ_ADC_REGULAR_READ_WHILE_INJECTED.md` (ПК-1,
область ADC-ТЗ заморожена 02.10.2026) — см. §2, пакеты не дублируются.

Источник требования — физический прогон стендового пакета инжекции ПК-3
(`ai3/inject-harness-publish`, `docs/INJECTION_PLAN_20261001.md`). Гейт
предусловий процедуры обязателен и опирается на `cv`: смещение VBUS в прошивке
печатает **только** ответ `cv` (`a?` — только `offset_i1`, `@ADC:CAL` — только
`i1/i2/ires`, `@ADC:STATUS` — `offset_i1` и период потока). Пока `cv` не
проходит, гейт fail-closed запрещает инжекцию, то есть **вся процедура инжекции
заблокирована** (лог `build/inject_preflight{,2,3,4}.log`, `build/ready_before.stdout`,
`build/diag_cv_noise.log` на ПК-3).

## 1. Что не работает сейчас (живые данные, стенд ПК-3, 02.10.2026)

Цель — обесточенная и разряженная шина: сырой VBUS 19…24 отсч, `MOE1=MOE8=0`,
`CCER=0`, `@BRK:valid=0`, `FAULT=0`, `uart_trunc=0`. Backup Flash перед опытом:
sha256 `2cbab38a9182a48e1537bd5dfeb16888772514cdf987c37cc6a5fb93659329e2`.

| 1.5 | ранее наблюдались и выбросы в сам порог | `a`: 24/**40**/22/23/24 (разброс 18 отсч) | решение по максимуму при пороге 40 отсч ≈ 4 В неустойчиво: порог стоит в размахе канала |

Сырые данные (sha256 всех артефактов, выдержки логов, границы доказательной базы) —
`docs/TZ_CV_VBUS_OFFSET_ROBUST_EVIDENCE.md`.

Код, отвечающий за отказ:

* `src/adc.c:535-561` `ADC_CalibrateVbusOffset()`: цикл 256 сэмплов
  (`ADC_OFFSET_SAMPLES`), решение по **максимуму** — `maxraw > ADC_VBUS_OFFSET_MAX_RAW`
  (40 отсч ≈ 4 В) ⇒ `rc=-2` (`src/adc.c:553`); смещение — среднее `sum/valid`
  (`:558`), то есть испорченный сэмпл сдвигает и значение;
* `src/adc.c:199-227` `adc_regular_read()`: на **каждом** вызове переписывает
  `SQR1` под нужный канал и стартует `ADSTART` (гейт по `JADSTART` — `:208`), то
  есть 256 раз за вызов `cv` канал переключается между шунтом и VBUS;
* `src/adc.c:609`: тот же одиночный regular-чтение VBUS встроено в `ci`-окно
  (отсюда наблюдаемый `vbus_mv=10476`);
* порог и его смысл зафиксированы в `docs/TZ_VBUS_OFFSET_CALIBRATION.md` §3
  («`cv` отказывается (`rc=-2`), если max raw > `ADC_VBUS_OFFSET_MAX_RAW`
  (40 отсч ≈ 4 В) — fail-closed: при поданном звене калибровка не „зашьёт“
  реальное напряжение в смещение»).

## 2. Связь с соседним ТЗ (не дублировать)

`docs/TZ_ADC_REGULAR_READ_WHILE_INJECTED.md` (ПК-1) решает соседнюю задачу:
регулярное чтение при взведённой injected-цепочке; там R1 — новый путь чтения
без перезаписи `SQR1`/`JSQR`, M1/M2 — гипотезы механизма, порядок «RED → R1-R9».

Настоящее ТЗ задаёт **контракт самой `cv`**: устойчивое решение + возможность
диагностировать отказ, и совместимо с любым из M1/M2 того ТЗ:

* если к моменту реализации R1 соседнего ТЗ уже влит в `main`, `cv` **обязан**
  использовать новый путь чтения (`ADC_ReadRegularWhileArmed` и т.п.) и не
  заводить второй механизм;
* если нет — правка остаётся внутри `ADC_CalibrateVbusOffset()` и **не меняет**
  поведение `adc_regular_read()` для остальных вызывающих (`c`, `ci`, кадры) —
  иначе пакет расширяет область и останавливается (§5.1 соседнего ТЗ);
* при параллельном исполнении это ТЗ вливается вторым и делает rebase.

## 3. Контракт (что должно быть верно после пакета)

**R1. Решение — по устойчивой статистике, не по максимуму.** Смещение = медиана
годных сэмплов; отказ, если медиана выше `ADC_VBUS_OFFSET_MAX_RAW`. Порог **не
повышается** (40 отсч ≈ 4 В): семантика fail-closed «вход не на нуле»
сохраняется, меняется только статистика решения.

**R2. Одиночные выбросы не должны ломать калибровку, но и не должны
«размывать» смещение.** Смещение считается по статистике, устойчивой к
выбросам; при доле сэмплов выше порога более X % калибровка отказывается
(`rc=-2`) — X обосновать (ориентир ≤ 5 %; живая шина 5 В даёт ~100 % сэмплов
выше порога, испорченные выборки — единицы процентов). Фактические числа
обязаны попасть в отчёт.

**R3. Независимость от предыдущего канала и вызова.** `cv` обязан давать один и
тот же результат до и после `ci 0/1/2`, `c`, `a` (живой контрпример — §1.4).

**R4. Повторяемость и идемпотентность.** Несколько `cv` подряд при неизменном
стенде → одинаковый `offset_vbus`, `rc=0`. Отказ не портит ранее измеренное
значение (действующее правило сохраняется).

**R5. Диагностируемость отказа.** Строка отказа обязана нести числа решения
(медиана, максимум, доля выбросов, число годных сэмплов) в **дополненных
полях** `@ADC:CV:FAIL:...`: префикс `@ADC:CV:FAIL:rc=<0|-1|-2>` и коды
сохраняются, формат `@ADC`/`@ADC:STATUS`/`@ADC:CAL` **не меняется**
(`docs/TZ_VBUS_OFFSET_CALIBRATION.md` §4 остаётся совместимым по префиксу).

**R6. Identity и периферия.** `adc_config_signature` / `current_calibration_signature`
не меняются (эталон `0x26B9B97B` / `0x13552B12`), `.ioc` и
`src/protect.c`/`src/pwm.c` не правятся вообще.

## 4. Порядок работ (обязательный)

1. **Сначала доказательство (RED), потом правки.** T1–T4 воспроизводятся на
   текущем коде **без его изменения** (host, мок-регистры) + артефакт-лог
   прогона: без RED нельзя отличить «исправлено» от «и так работало».
2. Затем реализация R1–R6.
3. Затем физическая проверка на стенде ПК-3 (§7) — **только она разблокирует
   процедуру инжекции**; «на стенде всё хорошо» без сценария/лога проверкой не
   считается (AGENTS.md, «Проверка на плате»).
4. Ничего из §6 «что пакет НЕ делает» — не «попутно»: расширение области
   останавливает пакет и возвращает его на пересмотр ТЗ.

## 5. RED-доказательство и приёмка (hosted, `make test`)

Тесты на мок-регистрах (`tests/mocks_adc/`, `ADC_HOST_TEST`, хук
`ADC_HostRegularRead` — конвенция `Makefile:266-276`). Хук определяется в самом
тестовом файле и **уже умеет отдавать значение по номеру вызова**
(`tests/adc_ci_window_test.c:11-30`: счётчики `cnt1/cnt2`, VBUS = 1234); новые
тесты задают скриптованную последовательность тем же способом, расширение
`tests/mocks_adc/registers.c` для этого не требуется (если понадобится —
расширение входит в пакет).

| Тест | Сценарий мока | Сейчас (RED) | После пакета |
|---|---|---|---|
| **T1** порядок каналов | первый regular-сэмпл после перезаписи `SQR1` = 2065 (шунт), далее 22 | `rc=-2`, `offset_vbus` не обновляется | `rc=0`, `offset_vbus=22` |
| **T2** одиночный выброс | 1 сэмпл из 256 = 4094, остальные 22 | `rc=-2` | `rc=0`, `offset_vbus=22` (медиана не сдвинута) |

| **T4** живая шина (fail-closed) | все 256 сэмплов = 71 (≈5.0 В) | `rc=-2` | **`rc=-2`** — обязательный регрессионный гейт: правка, которая принимает живую шину, тест не проходит |

зелёный и на ветке, и на `main` после вливания. Пары «код → тест»:
`ADC_CalibrateVbusOffset()` (`src/adc.c:535-561`) ↔ T1–T3/T5, порог
`ADC_VBUS_OFFSET_MAX_RAW` (`src/adc.h`) ↔ T4, гейт `cv` в CLI (`src/cli.c:75-88`)

## 6. Что пакет НЕ делает

* **не повышает** `ADC_VBUS_OFFSET_MAX_RAW` и вообще не трогает пороги
  `PROTECT_*`: ослабить гейт «вход не на нуле» нельзя, меняется только
  статистика решения (T4 это проверяет);
* не меняет `src/protect.c`, `src/pwm.c`, законы FOC/V/f, `.ioc`, карту
  (`region_contains`, map selector, `margin`), `src/map_capture*`;
* не меняет формат `@ADC`/`@ADC:STATUS`/`@ADC:CAL` и бюджеты телеметрии
  (`docs/TZ_MOPT0_TELEMETRY_BUDGET.md`); provenance/свежесть кадра `a` — не
  этот пакет (это `TZ_ADC_REGULAR_READ_WHILE_INJECTED.md` §R5);
* не переписывает injected-последовательность (`JSQR`, ранги, дуальный режим);
* не «заодно» не переделывает `c`/`ci`/`adc_regular_read()` для других
  вызывающих (если пакет R1 соседнего ТЗ не влит — см. §2);
* не правит стендовые инструменты ПК-3 (`tools/bench_inject_check.py` — пакет
  ПК-1/ПК-3 `ai3/inject-harness-publish`, его гейт не ослабляется и не
  подстраивается под дефект прошивки).

## 7. Физическая проверка (ПК-3, no-HV) — шаг, разблокирующий инжекцию

1. Обесточить и разрядить шину; `MOE1=MOE8=0`, `CCER=0`, `@BRK:valid=0`,
   `FAULT=0` (проверяет сам harness, отказ — до любого измерения).
2. Прогон гейта (инструмент из `ai3/inject-harness-publish`):
   `py -3 tools\bench_inject_check.py --preflight-only --windows=3 --source-tol-pct=<X> --log=build\inject_preflight.log`
   Ожидаемо: `@ADC:CV:OK:offset_vbus=N`, остаток `raw−offset` медиана ≤ 9 /
   максимум ≤ 200 отсч, `rc=0`.
3. **Согласованность путей** (это ловило дефект): в том же прогоне
   `ci 0.vbus_mv` обязан соответствовать уровню `a` (разница в единицы отсч),
   а не «улетать» (живой контрпример: `a`=22…23 отсч ⇔ 2216…2317 мВ, а
   `ci 0` отдавал 10476 мВ). Повторить `ci 0`, `ci 1`, `ci 2`, затем `cv` —
   результат `cv` не должен зависеть от того, что было перед ним (R3).
4. Только после п. 2–3 — инжекция по §5 плана: I1
   (`build\inject_i1_raw.log`), затем I2; вердикт по точкам: |slope−1| ≤ 5 %,
   SNR ≥ 3, возврат нуля после снятия стимула; журнал — `build/run_injection.ps1`
   (`-Phase ready` / `i1` / `i2`, локальный helper стенда, в git не публикуется).
5. Отчёт: лог + sha256 залитого образа + паспортная точность источника.
   `ERROR ≠ PASS`.

## Приложение: как воспроизвести наблюдения §1

Инструмент публикуется пакетом ПК-3 (сначала `e4c9457`, затем приёмка ПК-1):

```bash
git fetch origin ai3/inject-harness-publish
git switch -c repro-cv ai3/inject-harness-publish     # только для проверки
py -3 tools/bench_inject_check.py --preflight-only --windows=3 \
      --source-tol-pct=1.0 --log=build/cv_red.log
```

На дефектном образе: `@ADC:CV:FAIL:rc=-2` во всех `CV_ATTEMPTS = 3` попытках
при сыром VBUS 19…24 отсч ⇒ `rc=1` (FAIL) и блокировка инжекции. На исправленном
образе ожидается `@ADC:CV:OK:offset_vbus=N` и `rc=0`.

Стендовый helper `build/diag_cv_noise.py` (расширенный read-only сбор `a`/`cv`/
`ci 0/1/2` с разбросом сэмплов) — локальный артефакт ПК-3, в git не публикуется;
если ПК-1 захочет иметь его как деливерабл для воспроизводимости, он выносится
отдельным небольшим пакетом (`tools/bench_vbus_noise_check.py` + pytest).
