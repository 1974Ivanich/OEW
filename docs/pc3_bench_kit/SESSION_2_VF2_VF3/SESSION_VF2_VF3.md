# SESSION VF-2A → VF-2B → VF-3 (baseline characterization). Что сделать и что вернуть

## Provenance (переносить в отчёт без изменений)

```text
SOURCE_COMMIT         = ab1274d3506587303672325089d58a72bb941564
SOURCE_BRANCH         = ai2/vf-telemetry-rate-fix
MAIN_AT_BUILD         = 11ad97daafd77b00fb995877732897d15e74f8e7
MAIN_UNTOUCHED        = YES
COMMISSIONING_RELEASE = 1

PHYSICAL_SESSION_STATUS = BASELINE / NOT YET QUALIFIED
MAIN_MERGE            = PENDING
```

Образ: `IMAGE/firmware.bin` (energize-сборка, `-DOEW_HS1_COMMISSIONING_RELEASE=1`).
Прошивка: `STM32_Programmer_CLI -c port=SWD -w IMAGE/firmware.bin 0x08000000 -v -rst`
(команда — как в вашем обычном процессе; сверьте порт/адрес под свой стенд).
Перед подачей мощности сверить `sha256sum firmware.bin` с `IMAGE/SHA256SUMS`.

## Почему образ собран из ветки, а не из main

Решение зафиксировано: **идём на стенд с образом из ветки**, не задерживая физику приёмкой.
Поля `commit` и `sd1/sd2` в формате `@VFLOG` есть только на ветке `ai2/vf-telemetry-rate-fix`
(`ab1274d`); в `main` (`11ad97da`) их нет, а критерий остановки «непрерывный `commit=0`» без
поля `commit` вычислить нельзя. Физические данные привязываются к `ab1274d`; после успешной
сессии ветка принимается в `main`, и уже оттуда выпускается следующий образ.

## Не смешивать в отчёте три разные сущности

| Сущность | Чем подтверждается | Чего не доказывает |
|---|---|---|
| **firmware qualification** (`ab1274d`) | CI `build-test` (success), тесты, контракт телеметрии | ничего про реальную физику |
| **physical baseline** (эта сессия) | осциллограммы, сырой лог `@VFLOG`, измеренный VBUS | не означает приёмку ветки в `main` |
| **production acceptance** | только процедура приёмки в `main` | — |

Успешная физическая сессия **не означает автоматически**, что `ab1274d` принят в `main`:
она даёт данные для такого решения.

## 1. Предполёт

```text
pp=3           (иначе n<->f и vmag врут; ВНИМАНИЕ: `p?` в этом образе — статус PWM,
               полюса подтверждаются командой `pp=3`, не `p=3`)
vfk=15,50      (дефолты; задать явно для протокола)
vf?
```

**Прошивать не нужно:** на плате ПК-3 уже лежит ровно этот образ (readback сверен побайтово с пакетом).
**После подачи 60 В сбросить inrush-защёлку командой `f`** и убедиться в потоке `@FOC`, что
`FAULT=0:FAULT_R=0` — иначе `vf=` вернёт `rc=-3` (fault latched). На стенде при подаче 60 В
наблюдалось `FAULT_R=18`. Команды `c`/`ch`/`iv` на этом образе не запускать: обесточенная линия
autotune заблокирована fail-closed (`@AT:ERROR:POWER_BLOCKED`), см. `START_HERE_PC3.md`.

Проверить в ответах: `pp=3`; в первой же строке `@VFLOG` — `sd1=1:sd2=1` (SD/EM_STOP-цепь
здорова; если `sd≠1`, `vf=` вернёт rc=−8 `pwm_enable/interlock` — это и есть проверка цепочки
защиты, а не ошибка оператора). Измерить и записать фактический **VBUS мультиметром**
(ожидается ~60 В; в логе `vbus` — сырой ADC, приведём после).

## 2. VF-2A — дифференциальный тракт (TIM1 vs TIM8)

```text
vf=50          (2.5 Гц, vmag ≈ 20 %, duty фазы 40…60 %)
vflog=40
```

Осциллограф: CH1 — выход инвертора 1 фазы U, CH2 — выход инвертора 2 **той же фазы**,
math CH1−CH2, DC, усреднение по нескольким периодам PWM. ~10 с после старта — на рампу.

Снять 4 точки (позиции маркеров — по значениям `du` из лога):

| точка в логе | ожидание CH1−CH2 |
|---|---|
| `du ≈ 50 %` | ≈ 0 В |
| `du ≈ 40 %` | −12 В (при VBUS 60 В) |
| `du ≈ 60 %` | +12 В |
| знак | совпадает со знаком `(du − 50 %)` |

Скриншоты — с видимыми V/дел и время/дел; на скриншоте должен быть виден идентификатор
канала/фазы. **Доказывает:** второй инвертор действительно инвертирует PWM (OCxM=7 при тех
же CCR), то есть дифференциальный закон OEW на железе. **Не доказывает:** ничего про FOC,
карту токов и качество контура.

## 3. VF-2B — реальный V/F-вектор

```text
vf=40          (2 Гц, vmag ≈ 19 %)
```
Сверить `du/dv/dw` из лога с осциллограммой (период огибающей duty = 1/f_e = 0.5 с; сдвиг
между фазами 120° эл.; `vmag` = амплитуда огибающей). При возможности — второй канал на
другую фазу для проверки 120°.

**Гейт:** VF-3 запускается **только после успешного VF-2B**. Если фазы/амплитуда не совпали
с телеметрией — VF-3 не запускаем, сначала разбираем расхождение.

## 4. VF-3 — ступени (только после успешного VF-2B)

```text
vf=40 → ~15 с → vf=100 → ~15 с → vf=200 → ~15 с → vf=300 → vf=0
```
Полный UART-лог сохранить **как есть**, без правок, в файл (например `session.log`).
Разбор: `py -3 SESSION_2_VF2_VF3\TOOLS\vflog_step_report.py session.log --pp 3 --settle-ms 10000`.

## Что вернуть на приёмку

1. `session.log` (сырой лог сессии) и вывод `vflog_step_report.py` по нему.
2. Скриншоты осциллографа (VF-2A: 4 точки; VF-2B: сверка фаз) с настройками развёртки.
3. Измеренный мультиметром VBUS и DC-напряжение блока питания.
4. Заполненный `SESSION_REPORT_TEMPLATE.md`.
5. Если был аборт — на какой команде и что в логе: `fault=`, `sd1/sd2`, `commit`, `drp`.

> **Важно (по фактам сессии 26.09):** на 2000-м тике (2.000 с) прошивка проверяет `|meas| < 5 rpm`
> и, если ротор не сорвался, **отменяет пуск молча** (`vf_control.c:217-227`) — в логе это ровно
> 50 строк `@VFLOG` и отсутствие `@VF:STOPPED`. Это не авария: при vmag ≈18 % (63 % рампы на 2-й
> секунде) срыв может просто не успеть произойти. Для сессии это значит: слабая попытка кончается
> обрывом потока ровно на 2.000 с — ожидаемый исход, а не дефект.
>
> **VBUS-колонка лога непригодна для приёмки** — см. A5 в `ACCEPTANCE_VF2A_VF2B.md`.
> **Знак:** во всех 13 возбуждённых прогонах ротор уходил против знака команды → до разрешения знака
> `fslip`/`vmag` как характеристику V/f не использовать.

## Критерии немедленного аборта

`fault ≠ 0` · `sd1/sd2` ≠ 1 (EM_STOP активен) · VBUS ниже порога защиты (< 8 В) ·
stall-watchdog (2 с) · ненормальный шум/вибрация/нагрев · непрерывный `commit=0`.

Единичные `commit=0` — норма (~0.2 % тиков на переходах фаз), не аборт.
В запланированном диапазоне `vmag ≤ 45 %` непрерывного `commit=0` быть **не должно**:
если появился — это выход за контракт апертуры (потолок ≈ 73 % шины), фиксировать и
останавливаться.

## Что эта сессия НЕ доказывает

Это baseline characterization, а не модификация регулятора. По её данным решается, нужен ли
процентный slip-limit, VBUS-normalization или soft current limiter. FOC, карта токов и
admission-гейты этой сессией не затрагиваются.
