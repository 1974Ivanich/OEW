# TZ2 M-tuning: addendum C — калибровка оффсетов до снятия identity

Статус: **protocol-level amendment**, оформлено отдельным пакетом (не правкой текущих
ожидающих веток). Зависимость по порядку влития: сначала `ai2/tz2-identity-intake`
(этот пакет построен на его tip и расширяет intake-гейт), затем этот пакет.

## Что уточняется

В протоколе сессии (`docs/TZ2_M_TUNING_SESSION.md` §2) preflight перечислен как
`sysinfo`, `p?`, `pdump`, `enc`, `mapcap identity`. По факту первого реального возврата
с платы выяснилось, что в этом списке **не хватает `c`** — калибровки оффсетов ADC, —
и без неё `mapcap identity` возвращает **переходное** состояние identity.

**Требование:** `c` выполняется **до** `mapcap identity` и **до** `mapload`; после любого
reset/инициализации MCU калибровку нужно выполнять заново.

## Почему (факты из кода)

`current_calibration_signature` (`ccs`) — CRC по константам шкалы плюс один бит
`ADC_OffsetsAreValid()` (`src/map_capture_port.c:152-170`; комментарий там прямо фиксирует,
что сырые оффсеты в подпись класть нельзя — они дрейфуют и делают подпись невоспроизводимой):

```text
offsets НЕ валидны (до c)  → 0xABE94C77 = 2884193399
offsets валидны   (после c) → 0x13552B12 = 324348690
```

Обе величины воспроизведены независимым расчётом CRC32 (0xEDB88320, init 0xFFFFFFFF, xorout
0xFFFFFFFF) по константам `ADC_DC_SHUNT_UV_PER_A=63000`, `ADC_CT_UV_PER_A=100000`,
`ADC_VBUS_DIVIDER=125`, `ADC_OFFSET_SAMPLES=256` и биту валидности — то есть наблюдаемые
значения объясняются полностью, без остатка.

Решающий аргумент — **собственное поведение прошивки**: `0x13552B12` — это константа
`MAP_CAPTURE_BOARD_CAL_SIG` board-профиля (`src/map_capture_profiles.c:207`, комментарий
«scale constants + valid=1»), и штатный путь сборки карты сверяет identity профиля с живой,
отказывая при расхождении (`main.c:348-352` → `@MAP:BUILD:BLOCKED:IDENTITY`). Значит, в
состоянии «до `c`» прошивка сама не станет строить карту: каноническое состояние — после
калибровки. Дополнительно `ADC_CalibrateOffsets()` вызывается на старте FOC
(`src/foc.c:580`), то есть в момент работы карты оффсеты валидны — артефакт с `valid=1`
описывает именно рабочее состояние.

`offsets_valid` — статический флаг, обнуляется при инициализации ADC (`src/adc.c:251`) и
устанавливается только успешной калибровкой (`src/adc.c:517`). Отсюда требование повторять `c`
после каждого reset.

## Что меняется в инструментах

1. **Intake-гейт**: добавлено правило `I12` (калибровка выполнена до снятия identity):
   в логе обязательны эхо `c`, ответ `@ADC:STATUS:offset_i1=…` и `ccs`, равный каноническому;
   `c` после `mapcap identity` — нарушение. Каноническое значение задаётся `--expect-ccs`
   (по умолчанию константа board-профиля), т.е. при смене констант шкалы правило обновляется
   явно, а не «само».
2. **Протокол сессии** (§2): preflight дополняется командой `c` до `mapcap identity`.
   Порядок в сессии: `sysinfo → p? → pdump → enc → c → mapcap identity → mapload → …`

## Что НЕ меняется

- Требование неэнергичности входного шага: `c` требует остановленного PWM
  (`src/cli.c:61-66`: `err: PWM running — stop FOC/Vf first`), что в preflight уже так.
- Проверка identity в момент загрузки (`CurrentMap_LoadMeasured`) и отсутствие её перепроверки
  в рантайме: загруженная карта после калибровки не инвалидируется — это зафиксировано как
  факт, но менять поведение прошивки этим пакетом не предполагается.
- Никакие пины/флаги/`main` не затрагиваются.

## Сопутствующая hygiene-находка (не блокер)

Манифест первого возврата (`SHA256SUMS.txt`) записан с CRLF: `sha256sum -c` в POSIX-окружении
на нём падает (`'file'$'\r'`). Intake-гейт строки триммит и вердикт даёт верный, но
для независимой сверки на POSIX-машине манифест следует писать с LF. Отдельного пакета
не требует — достаточно требования в чек-листе возврата.
