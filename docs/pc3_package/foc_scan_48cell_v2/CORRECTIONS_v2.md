# CORRECTIONS_v2 — дефекты ред. 1 и их правки

Аудит проведён **до** запуска скана (пакет в ред. 1 не прогонялся на стенде).
Ссылки — на замороженный образ `ab1274d` (тот, что заявлен в §1 протокола);
проверка — через `git show ab1274d:<файл>`, а не по памяти.
Итог: SHA-256 архива совпадал с заявленным, внутренние проверки ред. 1 проходили,
но редакция была **небезопасна к запуску**: шкала метрики уезжала в 8.5 раза,
автостоп по `FAULT` был мёртв, амплитуды не отправлялись.

## B1. Шкала: `TCLK` вместо `CLK` (ошибка ×17)

`src/pwm.c:612` — `PWM_GetSysInfo()`: `tclk = get_tim_ck_int()/(TIM1->PSC+1)`.
`src/cli.c` — `@SYS:CLK=%lu:PSC=%lu:TCLK=%lu:…`, где `CLK` = `SystemCoreClock`
(`main.c`, `cli_pwm_sysinfo()`: `out[0]=SystemCoreClock`).

То есть `TCLK` — частота **счётчика**, а не тактовая таймера. Ред. 1 подставляла `TCLK`
в поле `--sysclk`, а `calc_expected.py` делила на `PSC+1` второй раз:

```text
ред. 1:  10_000_000/(16+1)=588 235 Гц  ->  f_pwm = 294.1 Гц,  f_JEOS = 588.2 Гц,  N(2 с) = 1176
ред. 2: 170_000_000/(16+1)=10 000 000 Гц -> f_pwm = 5000.0 Гц, f_JEOS = 5000.0 Гц,  N(2 с) = 10000
```

Правка: вход шкалы — `CLK`; `--tclk` используется только как сверка и при расхождении даёт
`MISMATCH` + код возврата 1; дополнительно `--pwm-expected 5000` сверяет декод с
`FOC_PWM_FREQ` (`src/pwm.c:13`) — ошибка такого класса больше не проходит «молча».

## B2. `RCR` выпал из формулы

`src/pwm.c:273` — `TIM1->RCR = 1u` (и `:293` для TIM8). При `RCR=1` и CMS=11
(центр-выровненный: 2 update-события за период) TRGO идёт с частотой
`2*f_pwm/(1+1) = f_pwm = 5000 Гц`, а не `2*f_pwm`. Ред. 1 считала `N_expected(2 с) = 1176`,
реальное ожидание — `10 000`; живая ячейка дала бы отношение `≈ 8.5`, правило кросс-чека
ред. 1 («отношение 2 или 0.5») не срабатывало → **ложный L2 PASS**.

`dump` RCR не печатает (`PWM_DumpRegs`, `src/pwm.c:629`) — поэтому в ред. 2 RCR фиксируется
как якорь на исходник образа (с явным указанием этого в `IDENTITY_AND_BASELINE.md`).

## B3. Живые поля брались не из той строки

Формат `@SYS` (`src/cli.c`): `CLK/PSC/TCLK/PLLCFGR/OVR/JEOS/TO/JQOVF/uart_drp/uart_trunc` —
полей `RUN`, `STATE`, `FAULT`, `CCR1` там нет. Они в `@FOC` (`src/telemetry_format.h`,
`FOC_TELEMETRY_FMT`): `…:Id: Iq: Id_ref: Iq_ref: VBUS: STATE: SPD: TH: sector: window:
CCR1: CCR2: CCR3: ADC_STATUS: FAULT: FAULT_R: FAIL: RUN: em_stop1: em_stop2`.
Ред. 1 парсила их из `sysinfo` → `None` → автостоп по `FAULT` не срабатывал никогда.
Правка: `@SYS` — для `JEOS/OVR/CLK/PSC/TCLK`, `@FOC` — для состояния; парсится **последняя**
строка `@FOC` внутри окна (без смешивания «до»/«после»).

## B4. Мёртвые стоп-проверки

Литералов `EM_STOP` и `SD active` в прошивке нет. Правильный источник — поля `em_stop1/2`
в `@FOC`, которые заполняются как `PWM_EmStop1IsHigh() ? 1u : 0u` (`main.c`): `1` = линия
высокая = здоровая, `0` = авария. Правка: стоп при `em_stop1==0 || em_stop2==0`; осознанное
исключение `--no-sd-stop` — только с записью в возврате.

## B5/B6. Амплитуды не отправлялись, семантика `i=` перепутана

Обработчик (`src/cli.c`): `sscanf(line, "i=%d,%d", &a1, &a2)` → `foc_set_current(a1,a2)` →
`FOC_SetIdRef(a1); FOC_SetIqRef(a2)` (кламп ±`FOC_I_MAX_MA` = 10 000 мА) → ответ
`@I:OK:Id=%ld:Iq=%ld`. Второй аргумент — **`Iq` в мА**, а не угол (ред. 1 писала `<deg>`).
Драйвер ред. 1 не отправлял `i=` вообще, поэтому 4 «амплитудные» ячейки были идентичны.

Правка: `Id = A·cos(θ)`, `Iq = A·sin(θ)`; отправка **после** `1` (первый `FOC_Start()`
вызывает `FOC_Init()` с `id_ref_ma = FOC_DEFAULT_ID_REF_MA` = 2000 мА, а сброса уставок
в `FOC_Start` нет — порядок «после `1`» исключает тихую подмену) и **до** окна;
ответ `@I:OK` и поля `Id_ref/Iq_ref` из окна пишутся в `cells.csv`.

## B7. `f` и калибровка нулей

Обработчик `f` (`src/cli.c`): при работающем FOC/Vf — отказ (`err: stop FOC/Vf first`);
иначе `rc = fault_request_clear()`, и калибровка выполняется **только если латч реально снят**:

```c
int rc = ops->fault_request_clear();
if (rc == 0) { ops->adc_calibrate(); ops->send_dbg("fault cleared\r\n> "); }
else { … rc=1: "no latched fault was active" … }
```

Поэтому утверждение ред. 1 «каждый `f` вызывает `ADC_CalibrateOffsets`» неверно:
`f` при чистом состоянии ничего не калибрует. Само FOC-стартование калибрует нули, но
только если они невалидны (`src/foc.c`: `if(!ADC_OffsetsAreValid() && ADC_CalibrateOffsets() != 0)
return FOC_START_CALIBRATION_FAILED;` — код `-3`). Правка: формулировка уточнена,
`f_list.txt` сохранён как отчётный файл, но драйвер ред. 2 не отправляет `f` **никогда**.

## B8. Подпись «не energize-сборка»

Коды `FOC_Start()` (`src/foc.h`): `0` OK, `-1` clock/fault, `-2` map_unverified, `-3` calib,
`-4` adc arm, `-5` pwm enable, `-6` params out of range. Ответ на `1` при отказе —
`@FOC:START:FAIL:rc=%d (0=OK -1=clock/fault … -5=pwm_enable …)`. Кода `-8` в FOC-старте
не существует (это коды V/f-старта команды `vf=`). Правка: стоп-текст драйвера
и `START_HERE` называют именно `rc=-5` (`FOC_START_PWM_ENABLE_FAILED`), а про `-7`/`-8`
сказано, где они живут.

## B9. Несуществующие команды в шаге 0

В `ab1274d` нет ни `rev`, ни `cv` (проверено поиском по `main.c` и `src/`), и нет строки
`@ADC:CV:`. ADC-телеметрия образа: `@ADC:I1=…:I2=…:Ires=…:VBUS=…`, `@ADC:STATUS:…`,
`@ADC:CAL:…`. Правка: проверка образа без перепрошивки — по `pdump`
(`@PWM:FULL:SYS=…:T1:PSC=…:ARR=…:CR1=…`; префикс группы только у первого поля — токенов
`T1:ARR`/`T1:CR1` в выводе образа нет), ожидание для `ab1274d`:
`SYS=170000000`, `T1:PSC=16`, `ARR=999`, `CR1` = `0x…E0` (CMS=11).
Строку `@PWM:FULL` печатает именно `pdump`, а не `p?` — этот второй слой дефекта разобран
в B11.

## B10. Отсутствие сайдкара

Ред. 1 передавалась одним ZIP; SHA-256 сверялся по переписке. Правка:
`scripts/build_foc_scan_48cell_pkg.py` пишет `<zip>.sha256` (формат `sha256sum`:
`<hex> *<имя>`) и умеет `--verify` (состав + хеши внутри `SHA256SUMS` + сайдкар).
ZIP детерминирован, поэтому один и тот же вход даёт один и тот же SHA-256.

## B11. Шаг 0 приписан не той команде (`p?` вместо `pdump`)

Класс тот же, что B9 (поля шага 0), но предмет другой: строка `@PWM:FULL:` была приписана
`p?`. Разбор по исходнику `ab1274d` (проверено `git show ab1274d:src/cli.c`):

| команда | что реально печатает | стр. |
|---|---|---|
| `p?` | `@PWM:CR1=%lu:CCER=%lu:BDTR=%lu:CNT=%lu` — **десятичные**, ни `SYS`, ни `PSC`, ни `ARR` | 76 |
| `dump` | `@PWM:DUMP:PSC=%lu:ARR=%lu:BDTR=0x%08lX:CR1=0x%08lX:CR2=0x%08lX:CCER=0x%08lX` (`CR1` hex) | 198 |
| `pdump` | `@PWM:FULL:SYS=%lu:CFGR=0x%08lX:T1:PSC=%u:ARR=%u:CCR=%u,%u,%u:BDTR=0x%08lX:CCER=0x%08lX:CR1=0x%08lX:CNT=%lu:T8:…` | 209–211 |
| `sysinfo` | `@SYS:CLK=%lu:PSC=%lu:TCLK=%lu:PLLCFGR=0x%08lx:OVR=%lu:JEOS=%lu:TO=%lu:JQOVF=%lu:uart_drp=%lu:uart_trunc=%lu` | 220 |

Следствие (ложный стоп): полей `SYS`/`T1:PSC`/`T1:ARR` в ответе `p?` **нет** — оператор либо
объявил бы «на плате другой образ» (скан не начался бы), либо подтвердил бы образ по
посторонним признакам. Второй слой того же дефекта — радиксы: `p?` печатает `CR1` в
десятичном виде (`224` = `0xE0`), а `dump`/`pdump` — в hex (`0x000000E0`); без явного указания
радикса значение `224` легко прочитать как «`CR1` с CMS=00» и получить неверный декод шкалы.

Правка ред. 2 (вторая итерация аудита): строка `@PWM:FULL` приписана `pdump`
(`START_HERE_PC3.md`, протокол §1–§2, `IDENTITY_AND_BASELINE.md`, `RETURN_TEMPLATE.md`,
`COMMANDS.md`); `p?` описан как дешёвая проверка «силовая выключена» в десятичных значениях
(`CR1=224`, `CCER=0`, `BDTR=7360` → MOE=0, `CNT=0`); поле `ARR` явно отнесено к `dump`/`pdump`
(в `p?` его нет); в `TOOLS/check_package.py` добавлено правило `check_step0_attribution`,
а в `tests/test_foc_scan_48cell_pkg.py` — негативный тест на эту ловушку.

## B12. Чтение энкодера: `eangle` вместо команды `enc`

Третья итерация аудита прошла по **всем** inline-токенам доков и сверила их с реальными
обработчиками образа (`strcmp(line, "…")` в `ab1274d:src/cli.c` / `main.c`). Живым оказался
один токен: `eangle`. Это не команда, а поле строки `@VFLOG`
(`src/telemetry_format.h`: `…:eangle=%u:espeed=%ld:eerr=%u:…`) — формат V/f-логирования,
который включается командой `vflog=<10..1000>` и к FOC-скану не относится.

Реальное чтение энкодера в образе — команда `enc`:
`@ENC:angle=%u:speed=%ld:period_us=%lu:pulse_us=%lu:err=%u` (`src/cli.c`; `angle` — 14 бит,
16384 = один механический оборот).

Следствие дефекта: оператор либо искал бы `eangle` и не нашёл его, либо включил V/f-логирование
перед FOC-сканом (лишняя команда смены режима + поток `@VFLOG` в UART поверх телеметрии окна),
а шаг 4 («подтвердить 10° электрических по энкодеру») остался бы без измерения — ровно то,
что протокол запрещает делать «на глаз».

Правка ред. 2: в протоколе §3 и `START_HERE_PC3.md` (шаг 2 и шаг 4) названа команда `enc` /
`@ENC`; поле `eangle=` явно помечено как V/f-логирование; в `TOOLS/check_package.py` добавлено
правило `check_command_vocabulary`, в `tests/test_foc_scan_48cell_pkg.py` — негативный тест.

## B13. Шаг 0 без машинного вердикта («софтом проверить нельзя»)

`CORRECTIONS_v2.md` (первая итерация ред. 2) заявляла: «доказательства, что образ на плате —
именно `d2bc0439…`: это доступно только на стенде (шаг 0), в пакете нет способа проверить это
софтом». Это неверно дважды. Во-первых, живой образ сам печатает якоря identity, и их
достаточно для однозначного вердикта: `pdump` даёт `@PWM:FULL` (`SYS`, `T1:PSC`, `ARR`, `CR1`),
`sysinfo` — `@SYS:CLK`, `a?`/`breakdiag` — статус, `enc` — `@ENC`. Во-вторых, «проверил глазами»
вердиктом не является: оператор сравнивал строки вручную, поэтому ошибка чтения (см. B14)
оставалась незамеченной ровно так же, как осталась незамеченной ложная атрибуция строки
шага 0 в B11, и результат шага 0 было нельзя воспроизвести при разборе возврата.

Правка ред. 2 (вторая итерация аудита): добавлен `TOOLS/check_step0.py` — read-only инструмент
шага 0. Он либо разбирает снятый транскрипт (`--log <файл>`), либо читает образ с порта
(`--port COM4`), сам отправляя **только** разрешённые команды (`sysinfo`, `a?`, `pdump`, `p?`,
`dump`, `breakdiag`, `enc` — и никогда `1`, `i=`, `f`, `a`, `c`), сверяет `SYS`/`T1:PSC`/`ARR`/
`CR1`/`CCER`/`BDTR` **двумя радиксами и двумя источниками** (`pdump` — hex, `p?` — dec) и
печатает вердикт `PASS`/`FAIL`/`ERROR` (rc 0/1/2), записывая `step0_report.txt` и `result.json`.
`RCR` в отчёте помечен `NOT MEASURED`: его не печатает ни одна команда образа (§2), поэтому он
остаётся якорем на исходник `src/pwm.c:273`, а не «измеренным». В `TOOLS/check_package.py`
добавлено правило `check_step0_machine_verdict`: пакет не проходит самопроверку, если
`check_step0.py` отсутствует, его `--selftest` (1 положительный + 6 негативных случаев) не
проходит, пустой вход даёт `PASS` (а не `ERROR`) или доки шага 0 не называют инструмент.

## B14. Несуществующие токены `T1:ARR`/`T1:CR1` (префикс группы только у первого поля)

Тот же класс, что B11, но внутри самой строки `@PWM:FULL`. Формат (`src/cli.c`, команда `pdump`):

```text
# эту строку печатает команда pdump (не p?):
@PWM:FULL:SYS=…:CFGR=…:T1:PSC=…:ARR=…:CCR=…,..,..:BDTR=…:CCER=…:CR1=…:CNT=…:T8:PSC=…:ARR=…:…
```

Префикс группы `T1:`/`T8:` стоит **только у первого поля** (`PSC`), а остальные поля идут
голыми (`ARR=`, `CCR=`, `BDTR=`, `CCER=`, `CR1=`, `CNT=`). Токенов `T1:ARR`/`T1:CR1`/`T1:CCER`/`T1:BDTR`/`T1:CNT` и их T8-аналогов в выводе нет, и поиск по ним даёт «пусто» → ложное «на плате другой образ» и остановку скана на исправной плате.

Правка ред. 2: во всех документах шага 0 (`README.md`, `START_HERE_PC3.md`, `COMMANDS.md`,
`FOC_SCAN_48CELL_PROTOCOL.md`, `IDENTITY_AND_BASELINE.md`, `RETURN_TEMPLATE.md`) указана
реальная форма (`SYS=170000000`, `T1:PSC=16`, `T8:PSC=16`, `ARR=999`, `CR1=0x…E0`), а сами
токены, которых в выводе нет, больше не выдаются за поля. `TOOLS/check_step0.py` разбирает
группы (`_group_fields()`, `full_groups()`) и сверяет `ARR`/`CR1`/`CCER`/`BDTR`/`CNT` внутри
группы. В `TOOLS/check_package.py` добавлено правило `check_step0_field_names`: доку, которая
ссылается на `T1:ARR`-подобный токен без пометки «в выводе нет», пакет не пропускает.

## Чего в ред. 2 по-прежнему нет (осознанно)

* проверки `FAIL=0` как стоп-условия: `FAIL` = `FOC_GetStartupFailReason()`, в начале разгона
  ненулевое значение ожидаемо → пишется как warning (это L4-критерий, читается глазами);

  по UART не читается. Вместо этого есть **машинный вердикт шага 0** (`TOOLS/check_step0.py`)
  по якорям identity: `SYS=170000000`, `T1:PSC=16`/`T8:PSC=16`, `ARR=999`, `CR1=0x…E0` →

  образ, и ошибку чтения строки (дефект B13), но байтовое сравнение не заменяет.

## B15. Блокирующее чтение порта (шаг 0 и скан висели насмерть)

Найдено **на стенде** при первом запуске шага 0 (2026-10-03, COM4 =
`STMicroelectronics STLink Virtual COM Port`): ред. 2 уже после правок B13/B14
оставалась неработоспособной на живой плате.

```text
py -3 TOOLS/check_step0.py --port COM4 --out .\step0
→ порт открылся, команда `sysinfo` ушла, дальше процесс висит бесконечно
```

Причина: `serial.Serial(port, baud, timeout=0.2)` + `read(4096)` (тот же путь
в `scan_48cell.py`: `Link.__init__`/`pump`). На этом VCP блокирующий `read()`
с `timeout` **не возвращается вообще**: `Ctrl+C` — единственный выход,
автостопов нет. Тот же стенд через независимый канал (`.NET SerialPort`)
читается штатно — `@SYS:CLK=170000000:PSC=16:TCLK=10000000:…` и поток `@FOC:…`
каждые 100 мс, то есть неисправен не стенд, а путь чтения в инструменте.

Второй слой дефекта (нашёл регрессионный тест, а не глаза): транскрипт, снятый
с порта, был **неразбираем** — маркер склеивался с ответом (`'> sysinfo'` +
`'@SYS:…'` → строка `> sysinfo@SYS:…`, не начинающаяся с `@SYS`), а в заголовок
подставлялся сырой `eol` (`\r\n`), из-за чего разрывалась строка заголовка и
первый маркер присоединялся к ней.

Третий слой (нашёл уже живой прогон после первой правки): лимит приходилось
делать **жёстким**. Если считать «тишину» и сбрасывать таймер на каждом
принятом пакете, то при непрерывной телеметрии `@FOC` (каждые 100 мс) пауза
`quiet` не наступает никогда и захват снова висит насмерть — уже не на уровне
`pyserial`, а в логике инструмента. Поэтому `per_cmd_s` в `capture_port` и
`limit` в `Link.pump` — предел на команду/окно целиком, а `quiet` — только
ранний выход.

Правка ред. 2: порт открывается с `timeout=0` и `write_timeout=1`, буфер приёма
сбрасывается (в нём лежит периодическая телеметрия `@FOC`/`@SYS`), читаются
только уже пришедшие байты (`in_waiting`) порциями, завершение — по паузе
`quiet` или лимиту `limit`; маркер `> cmd` пишется отдельной строкой; `eol`
в заголовке — именем (`crlf`/`lf`). Тот же рецепт — в `Link`
(`TOOLS/scan_48cell.py`): окно и пост-мортем иначе зависали бы вместо чтения.
Регрессии: `test_step0_port_reader_is_nonblocking` (вердикт из снятого с порта
транскрипта = `PASS`) и `test_scan_link_is_nonblocking`; сверх того — живой
прогон шага 0 на стенде.

## B16. Гейт параметров двигателя не описан: `rc=-6` (`params_out_of_range`)

Найдено **на стенде** (2026-10-04, живой запуск шага 3, COM4, образ `ab1274d`): первый же
старт вернул не `FOC started` и не `rc=-5`, а третий по счёту гейт прошивки:

```text
> 1
FOC start blocked: motor Rs/Ls out of sane range (run autotune, then mp=/mpapply)
@FOC:START:FAIL:rc=-6 (0=OK -1=clock/fault -2=map_unverified -3=calib -4=arm
 -5=pwm_enable -6=params_out_of_range)
```

Причина — **штатный fail-closed прошивки**, а не дефект стенда: дефолтные параметры
(`FOC_DEFAULT_R_MOHM`, `FOC_DEFAULT_L_UH`) намеренно лежат вне «здорового» окна
(`AT_MATH_SANE_LS_MIN_UH`), поэтому без явного `mp=<Rs_mOhm>,<Ls_uH>` + `mpapply`
старт FOC запрещён. Окно гейта: Rs 10…100000 мОм, Ls 500…500000 мкГн.
Следующий гейт после параметров — карта реконструкции (`rc=-2 map_unverified`, см. B17).

Следствие для ред. 2: документация обещала только `rc=-5`, а «Проверка сборки» шага 0
трактовала любой иной ответ как «непонятно»; оператор не мог отличить «на плате не
energize-сборка» от «плата не подготовлена к FOC». Живая сессия встала ровно на этом:
`scan_48cell.py` корректно остановился автостопом на первой клетке, но ноль из 48 ячеек
был получен (сырые логи — `docs/evidence/scan_20261004_run1/`,
`docs/evidence/incident_20261004_hwbreak/08_post_scan_raw.log`).

Правка ред. 2 (эта редакция): таблица ответов на `1` (`rc=0`, `-2`, `-5`, `-6`) в
`START_HERE_PC3.md` и `COMMANDS.md`; поля `rc`, параметры FOC и состояние карты в
`IDENTITY_AND_BASELINE.md` и `RETURN_TEMPLATE.md`; правило самопроверки
`check_start_gate_codes` + негативный тест; шаг 3 прямо требует записать дословный
ответ на `1` и **не начинать** скан, пока `rc != 0`.

## B17. Второй гейт — карта секторов (`rc=-2`) — и порядок снятия аппаратного break

Найдено там же, тем же запуском, двумя слоями.

**Слой 1 (карта).** За параметрами стоит второй гейт (`CurrentRecon_IsReady()`): при пустой
карте старт возвращает `rc=-2 map_unverified`, а в телеметрии видно
`@FOC:run_id=UNSET:map_id=M0:map_crc32=00000000`. Ред. 2 нигде не объясняла, что карта
нужна для старта и как её получить; команда-источник (`mapcap`) в наборе стенда не
упоминалась. Проверено на плате (сырой лог —
`docs/evidence/incident_20261004_hwbreak/06_cmd_probe_raw.log`):

| команда | ответ в `ab1274d` | смысл |
|---|---|---|
| `mapcap identity` | `@MAP:IDENTITY:board=…:pwm=5000:arr=999:…:acs=…` | сборка умеет измерять карту |
| `mapcap status` | `@MC:STATUS:state=…:term=…:avail=…:detail=…` | состояние захвата (команда есть, отвечает) |
| `mapcap build=<profile_id>` | (в серии не запускалось; требует завершённого захвата: `mcarm=` + `mapcap run`) | штатный путь получить карту |
| `mapload` (без аргумента) | `unknown` | зонд сформулирован неверно: парсер ждёт `mapload ` + 994 hex — **см. B18** |
| `mpapply` | `@MPAPPLY:ERROR:-2` | без `mp=` применять нечего (ожидаемо) |

Форма «`mapload <994 hex>`» в образе **есть**: правильный зонд (`mapload 00`) отвечает
`@MAP:LOAD:FAIL:DECODE`. Это исправлено разделом **B18** ниже — утверждение «в образе нет»
из первой редакции этого раздела было ошибочным.

**Слой 2 (снятие латча после аппаратного break).** Правило §5 («стоп → `0` → снять питание»)
описывало только нормальный останов. После break (`FAULT_R=18` =
`PROTECT_FAULT_HARDWARE_BREAK`) штатное снятие латча требует **строгого порядка**:

1. `c` — калибровка нулей ADC, только при обесточенном PWM; до неё нули не сняты
   (`offset_i1=0`), и `|idc|` выглядит как ~26 А (артефакт);
2. `f` — сброс латча; иначе `PROTECT_RequestClear()` отвергает снятие как
   `PROTECT_CLEAR_VALUES_UNSAFE` (=4), потому что «ток» больше половины `FOC_I_MAX`.

Обе команды вне набора стенда ред. 2 (а `f` в нём прямо запрещена), поэтому ред. 2 их
**не добавляет**: документация фиксирует факт и порядок, а снятие латча остаётся действием
владельца стенда вне рамок пакета (в серии 2026-10-04 так и было: `c` → `f`,
`FAULT=0:FAULT_R=0`, сырой лог —
`docs/evidence/incident_20261004_hwbreak/07_recover_raw.log`).

## B18. «В образе нет `mapload`» — вывод из зонда неверной формы (поправка к B17)

Раздел B17 этой же редакции утверждал как факт: «команды `mapload` в образе НЕТ: внешний
артефакт карты не грузится». Основание было слабее, чем формулировка: на плату ушло слово
`mapload` **без аргумента**, и она ответила `unknown`.

Так и должно быть: парсер образа распознаёт только строку с полезной нагрузкой
(`strncmp(line,"mapload ",8)` — `main.c`), поэтому голое слово проваливается в общий
`unknown` независимо от того, скомпилирована команда или нет. `unknown` на команду без
аргумента — не доказательство отсутствия.

Проверка правильной формы (2026-10-04, COM4, тот же образ; зонд **читающий**, ничего не
записывает и не энергирует; сырой лог — `09_capability_probe_raw.log`, разбор рядом —
`capability_probe.md`; оба в `docs/evidence/incident_20261004_hwbreak/`):

| зонд | ответ платы | что доказывает |
|---|---|---|
| `mapcap status` | `@MC:STATUS:state=0:term=0:cap=0:frames=0:dropped=0:periods=0:avail=0:detail=0:…` | путь `mapcap` скомпилирован и отвечает |
| `mapcap identity` | `@MAP:IDENTITY:board=7:pwm=5000:arr=999:trig=0x4F455731:off=0:dt=192:adc_clk=42500000:sample_x2=1281:res=0:acs=0x26B9B97B:ccs=0x13552B12` | скомпилирована ветка `#if OEW_MAP_L3` |
| `mapload 00` | `@MAP:LOAD:FAIL:DECODE` | команда **есть**; длина проверяется раньше разбора, карта не грузится, состояние не меняется |
| `mapcap build=` | `err: mapcap build=<profile>` | команда **есть**; пустой аргумент разобран как ошибка формы, действий нет |

Вывод: прошитый образ (`ab1274d` + флаги комиссионинга: `mapcap identity` и `mapcap status`
существуют только при `OEW_MAP_CAPTURE=1 && OEW_MAP_L3=1`, дефолты обоих — `0`) содержит
**весь** L3-путь: `mcarm=`, `mapcap run|drain|abort|status|identity|build=<profile_id>`,
`mapload <994 hex>`. То есть `rc=-2` — не «путь закрыт сборкой», а «карта ещё не загружена».

Дополнение к карте путей (проверяемое из кода, не из переписки):

* `mapcap build=<profile_id>` — не `<N>`: allow-list платы
  (`src/map_capture_profiles.c`, `MAP_CAPTURE_BOARD_PROFILE_ID 0x424F4152`), 12 вариантов
  `id = 0x424F4152 + sector*2 + window` (десятичные `1112490322…1112490333`); чужой id →
  `@MC:ARM:BLOCKED:PROFILE` / `@MAP:BUILD:BLOCKED:PROFILE`;
* сборка возможна только после завершённого захвата, иначе
  `@MAP:BUILD:BLOCKED:CAPTURE_STATE=…:TERM=…:AVAILABLE=…`; при расхождении identity —
  `@MAP:BUILD:BLOCKED:IDENTITY`. Порядок точки: `mcarm=` → `mapcap run` → `mapcap drain` →
  `mapcap status` → `mapcap build=` (`docs/ACCEPTANCE_LESSONS.md` §25.10);
* внешние артефакты от 08.09 (`мотор анализ\map_upload_pkg_20260908\*.bin`) несут
  `pwm=294`: это дефект D3 (двойной учёт `PSC`), и такие identity «отвергаются как
  устаревшие» (`src/map_capture_profiles.c:191-199`). Живая плата даёт `pwm=5000`, поэтому
  загрузка этих файлов закончится `@MAP:LOAD:FAIL:COMMISSION` — на этой плате карта
  берётся захватом на месте.

Чего этот зонд **не** доказывает (границы вывода, чтобы не повторять ошибку B18):
захват не запускался, поэтому неизвестны ни `@MC:ARM`/`@MC:RUN`, ни качество будущей карты;
`mapcap run` — **энергированный** burst из 8 импульсов, поэтому комиссионинг остаётся
действием владельца стенда (и, по §3 `START_HERE_PC3.md`, ему достаточно 24–36 В, а не 60 В).

Правка этой редакции: исправлены утверждения в `COMMANDS.md` и `START_HERE_PC3.md`
(таблица ответов на `1`, раздел «чего пакет не делает»), `IDENTITY_AND_BASELINE.md`
(новые строки `mapcap status`/`mapcap identity`/`mapload 00`), `RETURN_TEMPLATE.md`
(что записывать при подготовке карты) и правило самопроверки `check_map_path_claims`
+ 3 теста: доки обязаны называть арность `994`, не имеют права выводить отсутствие команды
из `unknown` на команду без аргумента и обязаны описывать профили BOAR и требование
завершённого захвата.
