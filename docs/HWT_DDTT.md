# HWT — проверки прошивки на цели через отладчик (DDTT)

Документ описывает инструмент `tools/hwt.py` и сценарии `tests/target/*.py`:
что они проверяют, чего не проверяют, как запускать и какие правила действуют
для ИИ-агента на стенде.

Идея (из спецификации DDTT, [stm32-gdbtest](https://github.com/ViacheslavMezentsev/stm32-gdbtest/blob/main/docs/ru/DDTT.md)):
действия, которые обычно делают руками в сеансе отладчика, записываются
сценарием в репозитории и выполняются инструментом с однозначным вердиктом и
машиночитаемым отчётом. **Тестовый код в прошивку не добавляется** — сценарий
останавливает цель в нужной точке, читает состояние по отладочной информации
образа и сравнивает с ожиданием.

## Как это устроено (транспорт)

```
Python-сценарий на хосте
        ↕ GDB Remote Serial Protocol (TCP)
   OpenOCD → ST-Link → SWD → STM32
```

GDB **не используется**: оба `arm-none-eabi-gdb` на ПК-1 собраны без поддержки
Python («Python scripting is not supported in this copy of GDB»), а сценарии —
это Python на хосте. Инструмент говорит с OpenOCD напрямую по GDB-RSP
(`tools/hwt_rsp.py`): останов/продолжение, аппаратные точки останова,
чтение/запись памяти и регистров, monitor-команды. Следствия:

* адреса символов берутся из ELF (`.symtab`), а не из DWARF;
* предел времени обеспечивает хост на уровне сокета — «плата не ответила» не
  может зависнуть в ожидании навсегда;
* символические выражения (`TIM1->BDTR`, `struct.field`) транспортом не
  поддерживаются: регистры читаются по адресу из `tools/hwt_stm32g4.py`,
  переменные — по адресу символа из ELF. API цели в таком случае **отказывает**,
  а не возвращает произвольное значение.

## Зачем это проекту

Две наших постоянных боли закрываются машинно, а не глазами:

| Симптом | Что отвечает HWT |
|---|---|
| «команда unknown», «плата ведёт себя странно» | сверка содержимого Flash цели с ELF (CRC-32 по секциям) — доказательство, что прошит именно этот образ, а не старый |
| «плата не отвечает / зависла» | точка CLI достигается дважды (цикл идёт), `CFSR/HFSR` пусты, `fault` не латчен |
| «а точно MOE снят / break не срабатывал?» | чтение `TIM1/TIM8` `BDTR/SR/CR1` на цели и сверка с инвариантами `src/pwm.c` |

## Установка и запуск

```bash
make hwt-doctor      # окружение: openocd, отладчик, образ, сценарии, порт RSP
make hwt-list        # список сценариев и их метаданные (без платы)
make hwt-preflight   # проверки без оборудования (то же гоняет CI)
make hwt-run         # запуск на стенде (нужны ST-Link и питание)
make hwt-sim         # прогон конвейера на заглушках (НЕ проверка на цели)
make backup          # дамп Flash + Intel HEX + SHA-256 перед экспериментом
```

Прямой вызов с параметрами:

```bash
python tools/hwt.py run --case HW_SAFETY_IDLE          # один сценарий
python tools/hwt.py run --state attach                 # без сброса цели
python tools/hwt.py run --out build/my_run             # свой каталог отчётов
python tools/hwt.py run --connect 127.0.0.1:3333       # свой RSP-сервер
python tools/hwt.py run --allow-injections             # разрешить инъекции (опасно)
python tools/hwt_backup.py --verify backup/flash_*.bin # сверка дампа без sha256sum
```

`--connect host:port` — подключиться к **уже запущенному** RSP-серверу вместо
запуска своего OpenOCD (так работает прогон против мок-сервера в тестах; так же
можно подключиться к стенду через SSH-туннель).

Коды выхода — единые для всех команд:

| Код | Вердикт | Значение |
|---|---|---|
| 0 | PASS / WAIVED | все проверки совпали; `WAIVED` — часть вердиктов снята записанным отказом (см. «Режим кампании»): прогон не падает, но PASS-ом не считается |
| 1 | FAIL | проверка не совпала (например, на плате другой образ) |
| 2 | ERROR | отказ входных данных, инфраструктуры или цели (нет связи, таймаут, нет инструмента) |

**ERROR никогда не превращается в PASS**: «плата не ответила» — это не «проверено».
**WAIVED никогда не превращается в PASS**: снятая отказом проверка остаётся в
отчёте с фактическим значением и пометкой отказа.

## Что делает `run` по шагам

1. **Входные данные и контракты** — разбор ELF, разбор сценариев через AST
   (без их выполнения), проверка контрактов (каждый объявленный символ должен
   быть в образе) и разбор реестра отказов (см. «Режим кампании»). Нарушенный
   контракт или битая запись отказа = ERROR до обращения к плате.
2. **Исключительный доступ** — блокировка на адаптер (`hwt_stlink.lock`):
   занятый отладчик даёт ERROR без ожидания; признак аварийного завершения
   прежнего владельца распознаётся и сообщается, чужие процессы не убиваются.
   (При `--connect` блокировка не берётся: сервером владеет кто-то другой.)
3. **Идентичность цели** — `DEV_ID` (DBGMCU_IDCODE) и размер Flash
   (`0x1FFF75E0`) читаются по RSP и сверяются с описанием стенда; при
   `policy = "deny"` (по умолчанию) несовпадение останавливает прогон.
4. **Сверка образа** — секции Flash (.isr_vector, .text, .rodata; writable
   секции исключены) читаются с цели и сверяются с ELF по CRC-32. Отчёт
   перечисляет, что именно проверено. Несовпадение = FAIL и сценарии не
   запускаются: «на цели старая прошивка → `make && make flash`».
5. **Сценарии** — исполняются на хосте, цель приводится в определённое
   состояние (`reset halt` или `halt`), точки останова ставятся аппаратные,
   после сценария снимаются. Предел времени контролирует хост: по исчерпании
   цель прерывается и остаётся остановленной, вердикт ERROR.
6. **Возврат цели в работу** — `monitor reset run`, результат попадает в отчёт.
7. **Отчёты** — `build/hwt/<прогон>/result.json` (id сценария, вердикт,
   проверки с фактическим и ожидаемым значением, инъекции, транспорт, адрес
   сервера, CRC/sha256 образа, факт симуляции) и `junit.xml`; лог OpenOCD и
   журнал по каждому сценарию (`case_<ID>.log`) рядом.

## Сценарии

| ID | Файл | Что проверяет |
|---|---|---|
| `HW_ALIVE` | `tests/target/hw_identity.py` | `$pc` в Flash, `$sp` в RAM, `CFSR`/`HFSR` пусты, `fault` не латчен |
| `HW_LOOP_PROGRESS` | `tests/target/hw_identity.py` | точка `UART_ReadLine` достигается повторно — цикл жив, плата не в HardFault |
| `HW_SAFETY_IDLE` | `tests/target/hw_safety_idle.py` | покой: `MOE` снят, `CEN`=0, `BIF/B2IF` не срабатывали, `BDTR` без запрещённых бит и с обязательными (`src/pwm.c`), `fault`/`fault_reason` пусты |
| `HW_BKIN_CONFIG` | `tests/target/hw_bkin_config.py` | Проверка 3A: `AF1.BKINE`=1, `AF1.BKINP`=0, `BDTR` `BKE`+`BKF[19:16]` (production) либо monitor-only, `BIF/B2IF` не срабатывали — сверка с `src/pwm.c` `timer_break_configured()` |
| `HW_MOTOR_PAIRS` | `tests/target/hw_motor_params.py` | шаг 1 паспорта: `pole_pairs` (`src/foc.c:128`) = шильдик (6 полюсов = 3 пары), и зеркало `g_motor_params.pole_pairs` (`main.c:705`) не разошлось с FOC |
| `HW_START_PATH_READY` | `tests/target/hw_motor_params.py` | шаг 4 паспорта, обе половины критерия: `g_motor_params.Tr_rotor_us` ≥ `FOC_SLIP_POLICY_MIN_TR_US` (`src/foc_slip_policy.h:8`) и `ENC_GetError() == 0` (байт `enc_error`, `src/encoder.c:50`) — иначе `Foc_Start()` идёт через V/f, и это пишется в отчёт явно; записью снимается только половина `Tr` (`VF_CAMPAIGN`, см. «Режим кампании»), половина энкодера — нет |
| `HWT_IMAGE` | встроенная | CRC-32 секций Flash цели против ELF |
| `HWT_TARGET_IDENTITY` | встроенная | `DEV_ID` и размер Flash цели против описания стенда |

**Поля структур читаются как «символ + смещение».** DWARF в образ может не
входить, а RSP-транспорт вычисляет только регистры ядра, поэтому
`t.value("g_motor_params.Tr_rotor_us")` даёт ERROR: сценарий обязан назвать
смещение сам — `t.word_at_symbol("g_motor_params", 16)`. Числа живут в
`tools/hwt_stm32g4.AT_MOTOR_PARAM_OFFSETS`, и их правильность держат две
проверки, потому что ошибка здесь не падает, а читает соседнее поле и выдаёт
правдоподобный PASS: контракт сборки `tests/autotune_params_layout_test.c`
(`_Static_assert` на `offsetof` — расхождение ломает сборку) и
`tests/test_hwt_motor_param_gate.py` (сверяет копию для сценария с этим
контрактом). Ни симулятор, ни мок-цель этого не поймают: они вычисляют адрес
из того же модуля и потому сдвигаются вместе со сценарием.

**Однобайтовые переменные читаются байтом, а не словом.** `t.byte_at_symbol("enc_error")`
берёт адрес из `.symtab` и требует, чтобы ELF объявлял размер символа ровно 1 байт:
чтение такой переменной словом (`t.word_at_symbol`) захватило бы соседние объекты
(в этой прошивке за `enc_error` идут счётчики захватов TIM2) и вердикт считался бы по
чужим данным — та же ошибка, что и при неверном смещении поля, только тише.

**Контрольная точка должна быть исполняемым символом.** При `-Os` функция может
инлайниться в вызывающего: имя остаётся в ELF (и проходит контракт), а точка по нему
не срабатывает никогда — сценарий получит ERROR по пределу времени, а не PASS.
На этой прошивке такой оказалась `CLI_ProcessLine`; рабочие точки — `UART_ReadLine`
(холостой цикл ожидания строки) и `hw_identity.py`.

Сценарии **только читают**. Инъекции (запись регистра ядра) реализованы, но по
умолчанию запрещены: нужно `safety.allow_injections = true` в описании стенда
**и** `--allow-injections`. Инъекция в силовой схеме может вызвать опасное
поведение оборудования (двигатель, 2× STEVAL-IPM20B) — включать только на
no-HV и с пониманием последствий; все инъекции со значениями до/после попадают
в отчёт. `force_return` (принудительный возврат из функции) этим транспортом
**не поддерживается** — нужна символическая отладка; сценарий получает ERROR,
а не подделку.

## Режим кампании: записанный отказ (waivers)

Гейт, который сегодня не может быть зелёным, не отключается и не ослабляется.
Вместо этого в репозитории лежит **запись отказа** — файл
`tests/target/waivers.json` (путь переопределяется `[run] waivers` в описании
стенда или `--waivers` у `run`/`preflight`), и каждый прогон отчитывается о
ней: `waiver_registry` (файл, sha256, записи) и `waivers.applied` /
`waivers.not_applied` в `result.json`.

| Правило | Чем держится |
|---|---|
| адресация точная | запись называет сценарий и **имя проверки**; маски запрещены |
| снимается только объявленное снимаемым | `t.check(..., waivable=True)` в сценарии; в проекте так объявлена ровно одна проверка — `Tr` в `HW_START_PATH_READY`; шильдиковые пары полюсов (`HW_MOTOR_PAIRS`) и состояние канала энкодера (`ENC_GetError() == 0`) снять нельзя ничем |
| отказ не бывает молчаливым | причина и компенсация обязательны, автор и дата обязательны; опечатка в имени поля, дубль, маска, не-ISO дата — ERROR до обращения к плате |
| снятое — не PASS | вердикт сценария и прогона становится `WAIVED`; в `result.json` проверка остаётся `ok: false` с фактическим значением, в `junit.xml` — `skipped`, в консоли — `~` и `[отказ]` |
| ERROR не снимается | отказ действует только на FAIL: «не дошли/не прочитали» остаётся ERROR |
| отказ сам выключается | когда проверка проходит (например, `Tr` измерена на шаге 4), запись печатается как «не понадобилась» — её пора снять, иначе это видно в каждом отчёте |
| запись бывает условной | условие, до какого события действует отказ, пишется в `compensating` словами «Условие снятия: …» и печатается вместе с записью в консоль, `result.json` и `junit.xml` — то есть в отчёте видно не только «отказ разрешён», но и до чего именно; бессрочных записей в реестре не держим |
| реестр — часть репозитория | отсутствие файла = обычный режим (отказов нет, гейт красный); путь и sha256 попадают в отчёт, так что локальную правку видно |

Текущая запись — `VF_CAMPAIGN`: снимает половину `Tr` сценария
`HW_START_PATH_READY`, пока кампания идёт через V/f (паспорт, шаг 4 не
выполнен). Запись **условная, не бессрочная**: условие снятия стоит в её же `compensating` (словами «Условие снятия: …») и печатается вместе с записью в консоль, `result.json` и `junit.xml` — отказ действует только на кампанию через V/f и только пока `Tr` не измерена. Компенсация записана в самой записи: прямой старт в этой кампании
не участвует, а при `Tr` ниже порога slip-модель даёт нулевую добавку
(`src/foc_slip_policy.c:13-17`). Вторая половина того же сценария — состояние
канала энкодера (`ENC_GetError() == 0`) — не объявлена снимаемой: ошибка
канала это неисправность, а не невыполненный шаг, и переход на V/f её не
компенсирует. Поэтому при `enc_error != 0` прогон остаётся FAIL и с записью,
а сама запись, адресованная этой половине, попадает в `waivers.not_applied`
(«не объявлена waivable»). Расхождение имён проверок ловит `preflight` (CI,
без платы) — предупреждением, а прогон перечисляет неприменённые записи в
`result.json` → `waivers.not_applied`.

## Описание стенда

`tests/target/stand.toml.example` — шаблон; рабочая копия
`tests/target/stand.local.toml` **не коммитится** (серийники, адреса, пути —
DDTT-6.3-1). Формат: секции `[probe]` (ожидаемые `device_id`, `flash_size_kb`,
`policy`), `[server]` (`openocd_cfg`, `gdb_port`, `rsp_timeout`, `exclusive`),
`[run]` (`state = reset-halt | attach`), `[safety]` (`allow_injections`).

## Границы: чего HWT не делает и не заменяет

* **Не подтверждает железо целиком.** Успешный сценарий — про цифровое
  состояние в конкретных точках; инициализация периферии, тайминги и
  физические причины отказов проверяются отдельно.
* **Не заменяет измерения.** Остановки, сброс и инъекции меняют поведение
  цели; форма сигналов, токи и время — это sigrok/осциллограф, а не отладчик.
* **Не программирует.** Запись прошивки — только `make flash`; HWT проверяет.
* **Симуляция и мок — не проверка на цели.** `--sim` прогоняет конвейер на
  заглушках, отчёт помечен `"simulated": true`. Тесты против мок-сервера
  (`tests/mock_rsp_server.py`) исполняют сценарии по-настоящему по протоколу,
  но данные отдаёт не кремний: вердикт такого прогона говорит об инструменте и
  сценариях, а не о плате.
* **Не отменяет ручную проверку на стенде** там, где нужен оператор: питание,
  нагрузки, приборы.

## CI

`make test-hwt` (входит в `make test`) без железа проверяет:

* `preflight` — контракты и CRC образа;
* симулированный прогон: корректный PASS, подмена секции образа → **FAIL(1)**,
  незакрытая точка останова → **ERROR(2)**, а не PASS;
* **сквозной прогон на мок-сервере RSP** (`tests/test_hwt_rsp.py`,
  `tests/test_hwt_on_target.py`): идентичность цели, сверка CRC образа,
  исполнение сценариев `tests/target/*` по протоколу, вердикты, отчёты, возврат
  цели в работу — без платы и без GDB;
* реестр отказов (`tests/test_hwt_waivers.py`, `tests/test_hwt_on_target.py`):
  неполная, размытая или дублирующая запись — ERROR, а не «отказов нет»;
  снятый гейт даёт `WAIVED` (не PASS), `ERROR` отказом не снимается,
  а проверка без `waivable=True` остаётся FAIL;
* pytest: `tests/test_hwt_*` (ELF32-разбор, метаданные, вердикты, отчёты,
  оффлайн-часть backup).

Настоящие проверки на плате в CI не выполняются: для этого нужен раннер со
стендом (схема «аппаратный CI» в DDTT). Пока это ручной шаг: `make hwt-run`.

## Резервная копия Flash

```bash
make backup                      # backup/flash_<штамп>.bin + .hex + SHA256SUMS.txt
make backup-verify FILE=backup/flash_20261002_120000.bin
```

Дамп снимается через SWD (`STM32_Programmer_CLI -u`), рядом кладётся Intel HEX
и контрольные суммы. Это чтение — ничего не стирается и не пишется. На ПК без
`sha256sum` сверка делается самим инструментом (`--verify`). Оффлайн-часть
(HEX + суммы) проверяется тестами в CI; сам дамп требует подключённого
отладчика.
