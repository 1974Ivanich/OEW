## 2. Непрерывность `seq` — WARN подтверждён, но разрывы **структурные**

| ряд | n | seq | span | пропущено | разрывов |
|---|---:|---|---:|---:|---:|
| 0/0 | 32 | 4…52 | 49 | **17** | 3 |
| 0/1 и далее все 11 рядов | 32 | — | 38 | **6** | 3 |

Итого пропущено 83 номера. Структура (пример ряда 1/0):
`95..102, 105..112, 115..122, 125..132` → блоки по 8, между блоками ровно по **2**
пропущенных номера. Это согласуется с фильтром/сеттлингом на смене вектора (4 grid-точки × 8),
а не со случайной потерей. Первый ряд дополнительно теряет 13 номеров в первом переходе —
это startup/hold.

Т.е. «seq continuity → WARN» корректен как **отсутствие доказательства непрерывного
захвата**: датасет не содержит сквозного цикла и cycle closure, а пропуски систематичны.
Читать это как «данные рваные случайно» — неверно; читать как «непрерывность доказана» — тоже.

## 3. Labels → углы: совпадение **0.00°** (12/12 рядов)

Угол каждой строки вычислен из её `cell` (Clarke: α=(2mu−mv−mw)/3, β=(mv−mw)/√3)
и сопоставлен с таблицей прошивки (`src/map_capture_profiles.c:225-230`):

| sector | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---:|---:|---:|---:|---:|---:|
| таблица, ° | 30 | −30 | 90 | 150 | −90 | −150 |
| датасет (mean), ° | 30.00 | −30.00 | 90.00 | 150.00 | −90.00 | −150.00 |
| \|вектор\| Q15, W0 / W1 | 9461 / 10672 | 9461 / 10672 | 9461 / 10672 | 9461 / 10672 | 9461 / 10672 | 9461 / 10672 |

Отклонение по всем 12 рядам: **0.00°**. Значит labels `0→30°, 1→330°, 2→90°, 3→150°,
4→270°, 5→210°` — **не произвольны**: это точные центры векторов таблицы прошивки
(нечётные кратные 30°). «Mapping risk» здесь не в углах, а в **порядке индексов**:
шаги по label = −60°, +120°, +60°, +120°, −60° — индекс является ключом по phase ordering,
а не номером сектора вдоль окружности. Подробно: `docs/FIRMWARE_TRANSITION_SAMPLING_SPEC.md` §1.1.

## 4. Почему «GROUP COVERAGE PASS» и «ADC CONVERSION PASS» **не являются доказательством**

| поле | факт в файле | что это значит |
|---|---|---|
| `margin` | **110 в 384/384** | константа контракта `MAP_CAPTURE_BOARD_MARGIN` (`src/map_capture_profiles.c:218`), а не измеренный запас |
| `settled` / `scope` | **1 / 1 в 384/384** | флаги квалификации; фильтр сработал для всех — проверяется пайплайн, не железо |
| `ict` | **0 в 384/384** | CT-канал в датасете пуст |
| `refu` vs `idc1` | **совпадают в 384/384** | «reference» не независим от измерения |
| `refv` vs `idc2` | **совпадают в 384/384** | то же |
| `refw` vs −(refu+refv) | **совпадает в 384/384** | KCL-остаток синтезирован по построению |

**Линейность «ADC-конверсии» (проверено отдельно).** OLS-фит `ref = a + b·idc1 + c·idc2`
по каждому ряду даёт остаток **0.000000 мА** для всех трёх каналов и всех 12 рядов: регрессия
тривиально точна, потому что `refu`/`refv` являются теми же числами, что `idc1`/`idc2`,
а `refw` — их суммой с обратным знаком. Остаток класса «~1.4 мА», если он где-то и наблюдался,
может объясняться только квантованием хранимой матрицы M или другим датасетом; в любом случае
он **не является свидетельством линейности ADC**, поскольку эталон копирует измерение.

Следствие: любые проверки KCL/остатков/маржи в этом датасете **тавтологичны** — они не могут
ни подтвердить, ни опровергнуть физическую привязку ADC к фазам. Поэтому «математическая
согласованность» — это согласованность **самого датасета**, а не согласованность ADC с фазами.
«NO OBSERVED WINDOW SIGN INVERSION» — корректная, но слабая формулировка: см. §5 (поле окна
в кадре ADC — копия объявленного значения, `src/adc.c:335-341` → `:123, 392, 547`).

### 4.1 Классификатор доказательности (воспроизводится инструментом)

Секция «статус доказательности полей» в `tools/verify_boar_geometry_dataset.py` печатает
машинный вердикт по каждому семейству полей:

| проверка | вердикт | основание |
|---|---|---|
| `ref` совпадает с измеренными каналами | **PASS как структурная целостность** | 384/384 |
| `refu == idc1` / `refv == idc2` | `reference_source=**DUPLICATE_MEASURED**` | 384/384 — эталон не независим |
| `refw == −(refu+refv)` | `reference_source=**KCL_SYNTHETIC**` | 384/384 — определён по построению |
| OLS residual = 0 | **EXPECTED / TAUTOLOGICAL** | фит точен по построению |
| ADC linearity | **NOT TESTED** | нет независимого эталона |
| ADC gain / offset | **NOT TESTED** | то же |
| физическая точность тока | **NOT TESTED** | то же |
| phase / channel mapping | **NOT TESTED** | нет controlled swap |
| KCL residual | **NOT INDEPENDENT** | см. строку выше |
| независимая токовая модель | **ABSENT** | эталон в датасете отсутствует |

**Формулировка, обязательная к использованию** (вместо «ADC conversion PASS»):

> Преобразование raw → engineering согласовано с заявленной формулой, однако точность и
> линейность ADC независимо не подтверждены, поскольку reference-каналы дублируют измеренные
> каналы.

Ни один из проверенных показателей этого датасета не проверяет: коэффициент усиления ADC,
offset, нелинейность, ошибку аналогового тракта, соответствие raw-кода физическому току,
правильность выбора ADC-канала, полярность и соответствие `idc1/idc2` реальным фазам.

## 5. Identity: 9 из 11 полей совпадают с текущим профилем, 2 — плейсхолдеры

Сравнение с `src/map_capture_profiles.c:187-219`:

| поле | датасет | board-профиль | вердикт |
|---|---|---|---|
| board / arr / trigger / toff / dt / clk / smp / res | 7 / 999 / 0x4F455731 / 0 / 192 / 42 500 000 / 1281 / 0 | те же | **OK** |
| `pwm` | **294** | 294 | OK как поле, **физически неверно** (реально 5 000 Гц; дефект формулы, спец. §5) |
| `acs` | 0x13572468 | 0x26B9B97B | **MISMATCH** — синтетический плейсхолдер |
| `ccs` | 0x24681357 | 0x13552B12 | **MISMATCH** — синтетический плейсхолдер |

`identity_matches()` сравнивает и `acs`, и `ccs` (`src/current_map_selector.c:72-87`), поэтому
артефакт, собранный из этого датасета **на текущей прошивке, будет отклонён** по identity
(класс `FAIL:COMMISSION` / `BLOCKED:IDENTITY`), пока датасет не пересобран на текущих
константах. Датасет относится к состоянию профиля **до** их уточнения (комментарии
`src/map_capture_profiles.c:202-208`: «was placeholder 0x13572468 / 0x24681357»).

## 6. Geometry-режим: конвейер **отвергает** этот датасет

Прогон настоящего host-конвейера на самом датасете:

```bash
make -f tools/map_artifact_writer_test.mk map-artifact-cli
tools/map_artifact_pipeline_cli.exe boar_geometry_dataset.txt <out_dir>
# -> map_artifact_pipeline_cli: pipeline failed (status 4, row 0/0)
# -> EXIT 1, артефакт не создан (fail-closed сработал корректно)
```

`status 4` — `MAP_PIPELINE_CERT_FAILED` (`tools/map_artifact_pipeline.h`). Точный код
certifier'а получен прогоном **самого** `src/map_region_certifier.c` на 12 рядах датасета:

| режим | результат по 12 рядам |
|---|---|
| `use_geometry=1`, adjusted 7500/9000/9000/9600 | **12/12: status 7 = MAP_CERT_VALID_OUTSIDE** |
| `use_geometry=1`, TZ 6000/10000/10000/14000 | **12/12: status 7** |
| `use_geometry=0` (legacy statistical) | 12/12: status 0 = MAP_CERT_OK, регионы `mu[7931..8453] mv[-261..261] mw[-8453..-7931]` |

Механика: `geometry_bounds_for_sector_window` требует среднюю фазу строго отрицательной
(`mv_max = -1`, `src/map_region_certifier.c:39`), а центры векторов кампании имеют среднюю
фазу **ровно 0** (`(8192, 0, −8192)` для sector 0, `src/map_capture_profiles.c:225`).
Вне региона оказываются 24 из 32 cells в каждом ряду (grid-точки ±4 CCR переводят среднюю
фазу в ±262, из них внутрь попадает только точка с отрицательной средней фазой).

Контрольный прогон того же датасета с `use_geometry=0`: **EXIT 0**, артефакт 497 Б
(`oew_map_v2.bin`) — и в его audit-JSON зафиксированы именно плейсхолдерные сигнатуры:

```text
"adc_config_signature": 324478056,   /* 0x13572468 — synthetic */
"current_calibration_signature": 610800471,  /* 0x24681357 — synthetic */
"pwm_frequency_hz": 294
```

Следствия для формулировок предыдущего аудита:

1. **«GROUP COVERAGE PASS» не может относиться к geometry-режиму** — в нём датасет не
   сертифицируется ни при одних из обсуждавшихся порогов. PASS возможен только в legacy
   (statistical) ветке, где пороги W0/W1 вообще не читаются.
2. Документ «adjusted zones» настраивал пороги **ветки, которая не производит артефакт**.
3. Артефакт, если он и был получен, несёт синтетические `acs/ccs` → на борту
   `identity_matches()` его отклонит (§5).

## 7. Амплитудные зоны: подгонка порогов вместо rebuild кампании

Числа из `docs/BOAR_AMPLITUDE_ZONES_ADJUSTMENT.md` **подтверждены точно**
(mod_q15 = max(|mu|,|mv|,|mw|) на `cell`):

| | W0 (sectors 0,3,4) | W0 (1,2,5) | W1 (все) |
|---|---|---|---|
| заявлено в документе | 7930…8454 | 8192…8454 | 8978…9503 / 9241…9503 |
| в файле | 7930…8454 | 8192…8454 | 8978…9503 |

Но: при **замороженных** порогах `docs/TZ_MAP_REGION_GEOMETRY_REFACTOR.md` §3
(W0 = 6000…9999, W1 = 10000…14000) **все 12 рядов попадают в window 0**
(mod ≤ 9503). Значит «Adjusted Zones (Option A: 7500…9000 / 9000…9600)» — это изменение
**контракта под существующие данные**. По TZ §3 смена порогов требует новой qualification
revision и повторной сертификации, а §6 Phase 5 прямо требует **пересобрать кампанию**
с центрами, совместимыми с метрикой (W1 ≥ 10000). Поэтому:

* «adjusted zones» нельзя использовать как доказательство геометрии;
* датасет в текущем виде подтверждает только внутреннюю согласованность пайплайна.
