## 2. Опровергнутые утверждения (не повторять в протоколах)

### O1. «EN1/EN2 управляются прошивкой (`GPIO_Init()` в `main.c` ставит HIGH)» — НЕВЕРНО
### O2. «Программно включить драйверы нечем → вторая независимая блокировка» — НЕВЕРНО

Оба — искажения одного и того же факта. Как есть:

- Прошивка **никогда** не драйвит PB4/PB5. Единственный `BSRR` в `src/` —
  `pwm_board_pins.c:18` (`gpio_bsrr_write`), вызывается только для **PB6 = TRIG**
  (`:66`, `:122`, `:127`). PB12/PD2 настраиваются входами BKIN с явным
  `PUPDR`-сбросом («no MCU pull on external SD net»).
- Это не блокировка, а архитектура стенда после демонтажа interposer:
  `pwm.c:230` — «No interposer/output buffers remain: timer outputs drive the IPMs
  directly»; `pwm_board_pins.h:15` — «removed interposer control and feedback signals».
- **Решающая проверка:** V/f на 60 В разгонял ротор (−120…−198 об/мин) при этом же коде,
  а `VFC_Start` → `PWM_Enable()` → `pwm_start_timers_direct()` поднимает только
  `CCER`/`MOE`/`CEN` (`pwm.c:233-240`). Значит для появления тока на обмотках прошивка
  EN трогать не обязана — драйверы в рабочем состоянии без её участия.

Практический вывод: energised-тест после снятия B1 будет **реально** energised.
Отсутствие управления EN в протоколе надо описывать как **внешнее условие стенда**
(что именно подаётся на EN1/EN2 и как их рубить), а не как возможность/невозможность
программного пуска.

### O3. «Нужна защита, работающая без `ADC1_2_IRQHandler`» — уже частично выполнено

Аппаратный путь существует и не зависит от NVIC:

- `PWM_Init`: `pwm_break_bits = TIM_BDTR_BKE | TIM_BDTR_BKF` для TIM1 **и** TIM8
  (`pwm.c:253-256`, запись в BDTR `:281`, `:300`), `AF1 |= BKINE` (`:283`, `:301`), `DIER |= BIE`.
- Активный низкий SD срывает MOE аппаратно. Именно этот путь срабатывал в прогонах,
  когда `AT_TestBegin` уже выключил `ADC1_2_IRQn` (`autotune.c:68`).

Не хватает **софтверного** контроля тока в отсутствие ISR (`PROTECT_CheckFrame` вызывается
только из ISR через `adc_dispatch_protect_frame`), а не защиты как класса.

### O4. «Достаточно `mapcap`/`mapload` — и гейты откроются» — неверно для production-сборки

- `mapcap_command` — `cli.c:278`; парсер `mapload` — `uart.c:16-18`; оба живут только при
  `OEW_MAP_CAPTURE=1 && OEW_MAP_L3=1`.
- Сборка default-deny без `OEW_HS1_COMMISSIONING_RELEASE=1` (`Makefile:336`).
- Этап A по протоколу требует «production `main` @ `7b84771`, без commissioning-флагов» →
  в этой сборке **ни `mapcap`, ни `mapload` недоступны**. Требование «сначала карта» и
  требование «production-сборка» взаимоисключающи в текущей системе флагов.
- V/f гейт проходит не по измеренной карте, а по статической таблице
  `VfcApertureContract[6]` (`vf_control.c:44`, `vf_control.h:33`) — то есть прецедент
  «доверенного контракта вместо измеренной карты» в коде уже есть.

## 3. Требования к разблокировке (что должно быть в проекте, не в этом документе)

Три условия, **одновременно**; без любого из них energised-тесты остаются BLOCKED.

### R1. Управляемый путь включения вместо `both_enable()`
- Явная функция с предусловиями и отказом по умолчанию, а не прямая запись в `BSRR`/`CCER`/`MOE`.
- Обязательные проверки: валидность контекста выборки, отсутствие fault-latch,
  ограничение duty, таймаут удержания, гарантированный `both_disable()` на любом выходе.
- Отделяемый включаемостью (флаг сборки/конфигурации), по умолчанию — выключен.
- **Не** восстанавливать `tim1_enable()`/`tim8_enable()` как есть: они удалены как мёртвые
  в `880df92` и не имели предусловий.

### R2. Софтверная защита тока, не зависящая от `ADC1_2_IRQn`
- Тесты намеренно отключают ADC IRQ (`autotune.c:68`), поэтому нужен собственный путь:
  опрос в цикле измерения до `both_disable()` **или** отдельный таймер-страж
  **или** явное, документированное решение «держим только аппаратный BKIN + внешний лимит БП».
- Любой вариант обязан срабатывать при зависании цикла, а не только на итерации.

### R3. Разрешённый источник контекста выборки для autotune
- Либо измеренная карта (тогда тесты гоняются в **commissioning**-сборке, а не в production),
  либо — по образцу `VfcApertureContract` — явно зафиксированный доверенный контракт для
  фаз autotune с обоснованием, почему он безопасен без измерений.
- Выбор «production-сборка + mapload» недостижим (см. O4); это нужно зафиксировать в
  протоколе явным запретом, а не молчанием.

## 4. Что из этого следует для протокола Этапа A

1. §6 пункт про EN переписать по O1/O2: не «управляются прошивкой» и не «включить нельзя»,
   а «прошивкой не управляются; состояние EN — внешнее условие стенда; рубильник/E-Stop —
   единственный способ обесточить драйверы извне».
2. §5: снять упоминание EN из условий `pp=3`.
3. §1: блокировка одна (B1), «двойной блокировки» нет.
4. В преамбулу — противоречие O4: пока Этап A требует production-сборку, `mapcap`/`mapload`
   недоступны, и ни один energised-шаг через них не откроется.
5. Сохранить силу имеют остальные замечания к v1.3: оценка тока по `Rs` вместо RL-переходного
   (реальный расчёт в комментарии `autotune.c:391-395` даёт ~18 мА при 50 мГн против порога
   `best < 30`), «300 мкс» вместо фактического цикла до 20 мс (`autotune.c:397-409`),
   допустимость выбора `AT_CH_IN` при том, что CT постоянку не меряет, и `I=` в
   `@AT:CH_DETECT:OK` — это максимум |Δ| от нуля, а не измеренный ток.

## 5. Чего этот документ НЕ утверждает

- Не утверждает, что `both_enable()` «плохой» и его надо включить: B1 — осознанный fail-closed
  (`CurrentMap_Select* = fail-closed`), введён в `cd776e6` как P0.
- Не даёт оценки, достаточно ли `VfcApertureContract`-подобного контракта для autotune —
  это отдельное решение с расчётом.
- Не является разрешением на прогон: статус Route B — **BLOCKED**.
